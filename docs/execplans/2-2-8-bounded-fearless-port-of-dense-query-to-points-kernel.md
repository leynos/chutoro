## Purpose / big picture

Chutoro scores Hierarchical Navigable Small World (HNSW) candidates through one
query-centric distance call. `DataSource::batch_distances(query, candidates)`
reaches `DenseMatrixProvider`, which detects that every pair shares a query
row, packs the candidate rows dimension-major into a 64-byte-aligned padded
block, and runs a packed "query to many points" Euclidean kernel. That kernel
decides how fast neighbour scoring runs.

The dense provider maintains that same coordinate loop five times over: a
scalar reference, an AVX2 body, an AVX-512 body (both generated by one macro),
a NEON body, and a nightly `std::simd` body. The pairwise kernels are a
*separate* set of five, deliberately out of scope here. Fearless SIMD 1.2
offers one safe, generic vector API whose native width is the hardware's, with
no project-owned `unsafe` and no per-architecture intrinsic spelling. If a
single generic body can replace the query kernels' per-architecture bodies
without changing a single distance, the provider becomes cheaper to maintain.

This plan decides that question by measurement rather than by argument. It has
two outcomes, and both are successful completions:

1. **Adoption.** The generic kernel preserves parity, executes on every backend
   it replaces, keeps complete-batch performance inside a pre-registered
   tolerance, and demonstrably reduces the maintained query-kernel surface. The
   redundant per-architecture query bodies are deleted for the backends that
   have native execution evidence.
2. **Null result.** Any gate fails, or the complete patch (including retained
   legacy bodies, dispatch, tests, and proofs) does not reduce the maintained
   surface. The experiment is reverted, the established path stays, and the
   measured or explicitly inconclusive result is recorded beside roadmap item
   2.2.8.

A caller observes nothing in either case. After the change, and equally after a
null result, this still holds for one query `q` and candidate rows `p_i`:

```rust
let distances = provider.batch_distances(0, &[1, 2, 3])?;
// Element i is the Euclidean distance from row 0 to row 1 + i,
// within the dense provider's established 1.0e-5 absolute tolerance,
// with any non-finite result reported as f32::NAN.
```

Terms used below:

- **Packed layout**: `DensePointView` stores one contiguous coordinate block per
  dimension, each block `padded_point_count` long, where
  `padded_point_count = point_count.next_multiple_of(16)`. Unused lanes hold
  `0.0`. The base pointer is 64-byte aligned.
- **Lane-per-candidate**: each SIMD lane accumulates one candidate point's
  squared differences across all dimensions. This is the existing shape of the
  packed kernel and of the proposed generic kernel.
- **Capability token**: a Fearless SIMD value (`Avx2`, `Avx512`, `Neon`) that
  exists only if the running CPU was proven to support the matching instruction
  set. A token is a proof, not a hint.
- **Legacy body**: a current per-architecture packed query kernel
  (`x86_simd.rs`, `neon_simd.rs`).
- **Invocation**: the cached decision of which implementation answers the next
  query-to-points call, either a token-bearing generic kernel or a legacy
  function pointer.

## Constraints

These are hard invariants. Violating one requires escalation, not a workaround.

1. **No public interface change.** `DataSource`, `DenseMatrixProvider`,
   `PointPair`, `distance`, `distance_batch`, `batch_distances`, the error
   types, and every existing public signature keep their shape and semantics.
   No Fearless SIMD token, vector, or mask appears in any public signature. The
   crate-internal `simd` module stays private
   (`chutoro-providers/dense/src/lib.rs:12`).
2. **No new public Cargo feature.** `fearless_simd` is an optional dependency
   activated only through the existing `simd_avx2`, `simd_avx512`, and
   `simd_neon` features by `dep:` entries, so no implicit `fearless_simd`
   feature is exposed. `--no-default-features` and the nightly
   `nightly_portable_simd`-only configuration must not pull the dependency in.
3. **Preserve the packed layout.** `DensePointView` keeps its 64-byte
   alignment, its 16-point padding unit, its zero fill, and its
   `from_row_indices` allocation policy. This plan does not change
   `point_view.rs` storage. It may extend one accessor's `cfg` list, and only
   if EP-M3's check shows a reachable configuration that needs it.
4. **Preserve the scalar reference.** `euclidean_distance_query_points_scalar`
   remains the numerical oracle and keeps its exact expression order.
5. **Preserve feature selection.** The existing selector
   (`dispatch::euclidean_backend`, priority AVX-512, AVX2, NEON, portable SIMD,
   scalar) remains the authority for backend eligibility and order. A Fearless
   kernel runs only where the selector already chose that backend and a safe
   token for it is available.
6. **Preserve the pairwise kernels.** `euclidean_distance`,
   `euclidean_distance_batch_pairs`' pairwise path, `EUCLIDEAN_KERNEL`, and
   `squared_l2_tail` are out of scope and must not change behaviour.
7. **No project-owned `unsafe` in new code, and no fused arithmetic.** No
   `assume_supported`, no `kernel!` intrinsic wrapper, no `core::arch`
   intrinsics, no `unsafe` block in the new module or in the new dispatch code.
   Separately, the kernel must not call `f32::mul_add`, `SimdFloat::mul_add`,
   or any other fused or relaxed operation: the contract is one separate
   multiply and one separate add per dimension, and `INV-no-contraction` is not
   satisfied by a handwritten fused call just because the compiler did not
   introduce one. Both prohibitions are enforced by the same source contract as
   the token rules (see `Verification plan`).
8. **No unrestricted dispatch.** `fearless_simd::dispatch!` must not be used: it
   can select an instruction set that a Cargo feature has excluded. Tokens come
   only from `Level::new()` or `Level::try_detect()` and the safe
   `as_avx2`/`as_avx512`/`as_neon` conversions.
9. **Calling-thread execution.** The kernel stays synchronous on the caller's
   thread. No Rayon task, no blocking pool operation, no index re-entry. This
   preserves ADR 0006's callback contract under `insert_mutex`.
10. **No new allocation.** The kernel allocates nothing. It writes only the
    caller's output slice.
11. **MSRV 1.89.0.** `Cargo.toml:19` declares it. The dense manifest currently
    does not inherit it (RFC 0001 footnote 8); this plan adds
    `rust-version.workspace = true` to `chutoro-providers/dense/Cargo.toml` so
    the package has effective metadata, as RFC 0001 requires.
12. **Authorized dependencies.** Production: `fearless_simd = "1.2"`, declared
    in
    `[workspace.dependencies]` and consumed only by
    `chutoro-providers-dense` with `optional = true`.
    `fearless_simd_macros = "0.1"` is authorized but is **not** used unless
    Decision D3 is revised. Development: `pretty_assertions = "1.4.1"` and
    `googletest = "0.14.4"`, dev-dependencies of
    `chutoro-providers-dense` only, authorized by the maintainer for this task,
    and each used only where it earns its place:
    `pretty_assertions::assert_eq` for readable diffs of long float-slice
    mismatches (**not** for bit comparison: it renders `Debug` decimal text, and
    distinct NaN payloads or `+0.0`/`-0.0` compare equal under it, so the
    bit-identity test uses `f32::to_bits()` explicitly); and `googletest`'s
    matchers in the policy enumeration, where a table of 320 cases needs to
    report the failing combination rather than a bare index. If EP-M2 finds
    either unnecessary, it is dropped and the manifest stays smaller — an unused
    dev-dependency is not added "for completeness". No other dependency, in any
    crate, is authorized.
13. **File size.** No source file may exceed 400 lines (`AGENTS.md`).
    `chutoro-providers/dense/src/simd/kernels/mod.rs` is 303 lines and
    `simd/dispatch.rs` is 232, so the new module must be its own file rather
    than an addition to those.
14. **Do not modify** `chutoro-core/**`, `chutoro-providers/text/**`,
    `chutoro-compile-contracts/tests/trybuild/**`, or `verus/**` except where a
    milestone names the file. Task 2.3.2 is out of scope.
15. **Historical documents stay untouched.** Completed ExecPlans, the RFC's and
    ADR's dated sections, and `docs/chutoro-design.md`'s existing dated
    implementation updates are amended only by appending new dated material.

## Risks

- **Risk: no AVX-512 and no AArch64 execution host.** The development host is
  an AMD Ryzen 9 3900 (Zen 2): AVX2 and FMA are present, `avx512f` is absent,
  and no AArch64 runner or cross toolchain is installed. RFC 0001 requirement
  T5 forbids substituting a backend without native execution evidence, so
  AVX-512 and NEON substitutions cannot be enabled from this host. Severity:
  high. Likelihood: certain. Mitigation: pre-register the AVX2-only enablement,
  report executed-versus-skipped backends explicitly in every milestone, and
  treat the maintenance gate as the deciding gate (R2 below).
- **Risk: the maintenance gate cannot pass while legacy bodies are retained.**
  RFC 0001 requires a missing token to fall back to "the same legacy query
  implementation that the existing selector chose", so every legacy body whose
  backend is not fully substituted must stay. With AVX2-only substitution the
  complete patch is very likely a net *increase*. Severity: high. Likelihood:
  high. Mitigation: this is a legitimate null result and is handled as success;
  open question Q3 asks whether deleting the AVX2 legacy body is acceptable,
  and only an explicit maintainer decision can change the rule.
- **Risk: complete-batch cost hides the kernel.** Packing, validation, and
  result transfer dominate small batches; the 2.3.1 profile found realistic
  HNSW buckets fragmented at 8 to 48 candidates. A faster kernel may not move
  the batch number, and an extra dispatch match may cost more than the kernel
  saves at 8 candidates. Severity: medium. Likelihood: medium. Mitigation:
  two-level measurement with separate tolerances, and a pre-registered report
  of packed-kernel regressions even when packing hides them.
- **Risk: compiler contraction changes results.** If LLVM contracts the separate
  multiply and add into a fused multiply-add, results diverge in the last bits
  and the bit-identity test fails. Severity: high. Likelihood: low. Mitigation:
  the reference Rust build does no fast-math and Rust does not contract without
  an explicit `mul_add`; the plan still requires disassembly evidence and a
  bit-identity test that a contracted build would fail.
- **Risk: `Avx2` is not `avx2`.** The token denotes x86-64-v3 (AVX2 plus FMA,
  BMI1, BMI2, F16C, MOVBE, LZCNT), so a CPU or virtual machine that reports
  `avx2` but not the full bundle selects AVX2 yet gets no token and runs the
  legacy body. Severity: low. Likelihood: low. Mitigation: the policy is a pure
  function tested over all token-availability combinations, and the fallback is
  the unchanged legacy body, so the outcome is a missed opportunity rather than
  a regression.
- **Risk: compile time and binary size grow.** Multiversioning and a second
  backend in one crate can increase both. Severity: medium. Likelihood: medium.
  Mitigation: record clean-build time and release binary size before and after;
  record them in `Outcomes & retrospective`; declare a null result if the
  growth is material and the maintenance reduction is not.
- **Risk: `#[simd]` macro cost.** `fearless_simd_macros` pulls procedural-macro
  dependencies into the dense crate for one function. Severity: low.
  Likelihood: low. Mitigation: Decision D3 uses the manual inlining route first
  and adds the macro only if disassembly shows the manual route fails to
  produce packed instructions.
- **Risk: benchmark noise on a shared host.** The host runs other agents'
  builds; load average has been observed above 20. Severity: high. Likelihood:
  high. Mitigation: the noise study in EP-M1 must satisfy the rule in
  `Noise establishment` at every gated size class before any candidate timing
  is accepted; otherwise the cell is inconclusive and recorded as such.
- **Risk: cfg drift in partial feature sets.** The new module's gate, the
  dependency activation, and `DensePointView::padded_point_count`'s existing
  `cfg` list (`point_view.rs:123-139`) must agree, or a partial feature build
  fails to compile. Severity: medium. Likelihood: medium. Mitigation: EP-M3
  enumerates and builds every supported feature combination, and the
  compile-contract tests are extended where a machine-checkable rule exists.
- **Risk: `cargo::unused_dependencies` fires in a partial feature set.** A build
  such as `--no-default-features --features simd_neon` on x86-64 enables
  `fearless_simd` through `dep:` while the kernel module may be `cfg`-excluded,
  so the dependency is compiled and never named. Severity: low. Likelihood:
  medium. Mitigation: EP-M3 builds the partial feature matrix and records the
  outcome.

  **Corrected mechanism.** This was first written as a gate failure under
  `RUSTFLAGS=-D warnings`. That is wrong: `cargo::unused_dependencies` is a
  *Cargo manifest lint*, not a rustc lint, so `-D warnings` does not escalate
  it. Measured on this host: a crate with an unused optional dependency, built
  with `RUSTFLAGS="-D warnings"`, warns and exits 0; only
  `[lints.cargo] unused_dependencies = "deny"` makes it fatal. The workspace
  has no `[lints.cargo]` table, so the warning is cosmetic here and cannot fail
  a gate. `#[allow]` cannot suppress a manifest lint, and `allow_attributes` is
  denied anyway.

  The correct fix is to compile the kernel module whenever any native feature
  is on, so the dependency is always named. The single rule replacing two
  contradictory drafts: **compile `simd/kernels/fearless.rs` whenever one of
  `simd_avx2`, `simd_avx512`, or `simd_neon` is enabled, and gate only the
  token variants by architecture.** The kernel is generic over `S: Simd` and
  names no token type, so it compiles on every target. If a residual warning
  remains, record it as cosmetic; do not add a lint policy change to this task.
- **Risk: cognitive complexity is now gated at 9 by a macro-aware lint.**
  `main` moved this from Clippy to Whitaker: `clippy.toml` no longer sets
  `cognitive-complexity-threshold`, and `dylint.toml` opts in with
  `[whitaker] experimental = ["macro_aware_cognitive_complexity"]` and
  `[macro_aware_cognitive_complexity] max_complexity = 9`
  (`docs/developers-guide.md` records that Clippy scores code after macro
  expansion and so counted branching the macro generated). The generic kernel's
  chunk loop plus dimension loop plus remainder is three nested constructs, and
  `choose_query_kernel`'s exhaustive match over backends × tokens × evidence
  risks crossing 9. Severity: medium. Likelihood: medium. Mitigation: EP-M2 and
  EP-M3 treat `make lint-whitaker` as a required gate, not an optional one, and
  fix a finding by extracting named helpers — never by raising the threshold,
  which the developers' guide explicitly forbids. If `choose_query_kernel`
  exceeds 9, split it into one predicate per backend rather than suppressing
  the lint.
- **Risk: lint friction.** The workspace denies `float_arithmetic`,
  `indexing_slicing`, `unwrap_used`, `expect_used`, `integer_division`, and
  `missing_docs_in_private_items`. Severity: low. Likelihood: high. Mitigation:
  the kernel uses `get`/`chunks_mut` idioms already present in
  `portable_simd.rs:41-52` instead of indexing, and any `#[expect]` carries a
  scoped reason.
- **Risk: doctests must import the documented item.** `main` added a style-guide
  rule: Rustdoc compiles a doctest as an external crate, so a bare call cannot
  resolve and each example needs a hidden `# use crate_name::item;` line
  (`docs/documentation-style-guide.md`). Any `///` example this work adds to
  the generic kernel or the policy function must follow it, and examples should
  run as doctests where they can execute. Severity: low. Likelihood: medium.
  Mitigation: EP-M2 and EP-M3 run `make test-doc`, which compiles doctests as
  external crates and is where this rule is enforced. The plan's own code
  snippets are plan text, not rustdoc, so they are unaffected.

- **Risk: MSRV drift in a caret requirement.** `fearless_simd = "1.2"` permits
  any 1.x, and a later 1.x may raise its MSRV. Severity: low. Likelihood: low.
  Mitigation: `--locked` builds, record the resolved version, and re-run the
  1.89 check at adoption.

## Surprises & discoveries

Reconnaissance findings that change what the implementation must do. Each is
recorded with its evidence so that a later reader does not have to rediscover
it.

- Observation: the `padded_point_count()` accessor is only compiled under
  `test`, `kani`, or a *legacy* SIMD feature plus architecture. Evidence:
  `chutoro-providers/dense/src/simd/point_view.rs:123-139`. Impact: less than
  the first draft claimed. That list already covers `test`, `kani`, and every
  native SIMD feature plus architecture pair, which is every gate the new
  kernel can compile under, and the kernel reads `coordinate_block(k).len()`
  rather than the accessor. EP-M3 step 3 therefore checks the one remaining
  configuration — `testing` or `cfg(test)` with no native feature — and extends
  the list only if that configuration is reachable. The earlier "EP-M3 must
  extend" was too strong.
- Observation: the x86 query kernels use **aligned** loads while the pairwise
  kernels use unaligned loads. Evidence: `_mm512_load_ps`/`_mm256_load_ps` at
  `simd/kernels/x86_simd.rs:139` and `:177`, against `*_loadu_ps` in the
  pairwise macro at `:43-44`. Impact: alignment is a load-bearing precondition
  of the current query kernels, not an optimization detail. The generic kernel
  reads through safe slice operations, which relaxes it; that is a change in
  the *precondition*, not in behaviour, and must be stated in the design update.
- Observation: no query kernel has a scalar remainder today; every one assumes
  the native lane width divides the 16-point padding unit. Evidence:
  `step_by($lanes)` over `padded_count` in `simd/kernels/x86_simd.rs:84` and
  `neon_simd.rs:60`; `out.chunks_mut(16)` in `portable_simd.rs:39`;
  `lane_output_count` only truncates writes (`simd/mod.rs:31`). The Kani
  harness hard-codes lane widths `[4, 8, 16]` (`kani_proofs.rs:129-137`).
  Impact: RFC 0001's "complete chunks and a scalar remainder independent of the
  padding width" is new behaviour, not a restatement, and it needs its own
  invariant and proof. **But it is unreachable on every backend this plan can
  enable.** `P` is always a multiple of 16, so for any lane width `L` that
  divides 16 — which is all of them: NEON 4, AVX2 8, AVX-512 16 — the loop
  leaves `start == P >= n` and the remainder is empty for every `n`. I
  enumerated `n` in `0..4096` for each width: zero non-empty remainders. Only a
  width that does not divide 16 (for example 32) can produce one. The remainder
  is therefore future-proofing, not shipped behaviour of this change, and the
  plan must not claim otherwise.
- Observation: the plan's own first-draft remainder lemma was wrong, and the
  error is a real implementation hazard. Evidence: with `n = 17`, `P = 32`, and
  `L = 16`, the first full chunk covers `0..16` and the loop advances `start`
  to 32, which is **greater than `n`**. A remainder loop written
  `for index in start..n` either panics or, if written with unsigned
  subtraction, wraps. The existing kernels never hit this because they iterate
  `padded_count` and discard writes past `out.len()` via `lane_output_count`
  (`simd/mod.rs:31`, `x86_simd.rs:97`). Impact: `L-chunk-partition` now states
  `start = L * floor(P / L)` and requires the remainder to be
  `min(start, n)..n`. The kernel must guard on `start < n` before iterating,
  which the `n = 17`, `L = 16` pair demonstrates. Because that guard makes the
  remainder empty for every shipping width, the remainder body is unexecuted by
  any integration test; it is exercised only by a direct unit test of the
  helper with a synthetic `start < n`, and by the Kani harness at `L = 32`.
- Observation: `Level` does not implement `Simd`, so the kernel cannot be called
  through a `Level` value at all. Evidence: compiler diagnostics on 2026-11-24
  from a scratch crate that called a `<S: Simd>` function with `Level::new()`;
  `error[E0277]: the trait bound fearless_simd::Level: fearless_simd::Simd is
  not satisfied`,
  listing `Avx2`, `Avx512`, `Sse2`, and `Sse4_2` as implementors. Impact:
  `FearlessToken` is structurally necessary, not stylistic, and the design must
  match on the level before it can call the kernel. It also means a
  `Level`-shaped cache would not compile, which the plan's `QueryInvocation`
  already avoids.
- Observation: RFC 0001's claim that the contract "requires zero distances for
  identical zero vectors" is stronger than what the code *asserts*. Evidence:
  `ZeroVectorPolicy::ReturnZero` is a declarative variant;
  `debug_assert_contract` only asserts the variant is still `ReturnZero`
  (`simd/semantics.rs:182-191`), and every zero-row fixture is compared through
  the same `1.0e-5` epsilon. The *property* nevertheless holds exactly:
  `0.0 - 0.0 = +0.0`, `(+0.0)² = +0.0`, `+0.0 + +0.0 = +0.0`, and
  `sqrt(+0.0) = +0.0`, which `finalize_distance` passes through unchanged.
  Impact: RFC 0001 F3 names this and one assertion discharges it, so EP-M2 adds
  a positive-zero check (`value == 0.0 && value.is_sign_positive()`) to the
  existing identical-zero-vector fixture rather than declining it. REQ-F3 is

## Decision log

- D1. Decision: the candidate is a single private generic function in a new file
  `chutoro-providers/dense/src/simd/kernels/fearless.rs`, gated on an existing
  SIMD feature plus architecture. Rationale: it sits beside the bodies it would
  replace, keeps `kernels/mod.rs` under the 400-line cap (303 lines today), and
  adds no public surface. The rejected alternative — extending
  `kernels/mod.rs` — pushes it past 400: the EP-M3 vocabulary alone is 74
  declaration lines before bodies and docs, and a faithful implementation
  measured 137, giving 440. Date/Author: 2026-11-24, planning agent.
- D2. Decision: the generic kernel loops chunk-outer and dimension-inner, reads
  each coordinate block through safe slice access, and covers the tail with a
  scalar remainder driven by the block length rather than by the padding unit.
  Rationale: this reproduces the existing lane-per-candidate arithmetic exactly
  (same per-lane operation order, same separate multiply and add), while making
  the kernel correct for any native width rather than only for widths that
  divide 16. The rejected alternative — mirroring `out.chunks_mut(width)` as
  the portable-SIMD body does — reads past the block when the native width
  exceeds the padded length, which a future 32-lane backend would trigger.
  Date/Author: 2026-11-24, planning agent.
- D3. Decision: do not add `fearless_simd_macros` initially; use the manual
  inlining route (`#[inline(always)]` plus `Simd::vectorize`). Rationale: the
  crate already dispatches itself, so the macro's multiversioning duplicates a
  decision the selector owns, and it pulls procedural-macro dependencies into a
  crate that currently has none. The feasibility probe made that cost concrete:
  declaring the macro crate without using it produced
  `cargo::unused_dependencies` for `fearless_simd_macros`, which under
  `-D warnings` is a gate failure. If EP-M2's disassembly inspection shows
  scalar code in the hot loop, the macro is added and the decision is revised
  with that evidence. Date/Author: 2026-11-24, planning agent.
- D4. Decision: obtain the token after the existing selector has chosen a
  backend, never instead of it, and never through `dispatch!`. Rationale: RFC
  0001 and ADR 0007 both require that public feature choices survive.
  `dispatch!` can enable an instruction set that `--no-default-features`
  excluded, so it is forbidden even though it is the library's documented
  convenience path. Date/Author: 2026-11-24, planning agent.
- D5. Decision: the substitution policy is a pure `const fn` over the selected
  backend, a token-availability record, and a compile-time execution-evidence
  set; the runtime step only converts real tokens. Rationale: it makes the
  eligibility rule exhaustively testable and Kani-checkable without modelling
  the library, and it makes the evidence gate auditable in source rather than
  in prose. The rejected alternative — branching directly on `Option<Token>` at
  the call site — is untestable without hardware. Date/Author: 2026-11-24,
  planning agent.
- D6. Decision: only the AVX2 backend is a substitution candidate on this host.
  AVX-512 and NEON compile, are selected by the existing selector, and keep
  their legacy query bodies. Rationale: RFC 0001 T5 requires native execution
  before enabling a replacement, and this host has no AVX-512 and no AArch64
  execution. Date/Author: 2026-11-24, planning agent.
- D7. Decision: level-1 (packed-kernel) measurement uses a
  `#[cfg(feature = "testing")]`, `#[doc(hidden)]` fixture in the dense crate
  that owns a packed view, a query, and an output buffer, and can run a named
  backend and kernel variant. `chutoro-benches` enables the `testing` feature
  in a **`[dev-dependencies]`** entry, not on its normal dependency:
  `docs/developers-guide.md:1476-1478` states that rule, and both existing
  consumers follow it (`chutoro-cli/Cargo.toml:38-40`,
  `chutoro-compile-contracts/Cargo.toml:33`). Cargo permits the same package in
  both tables, and bench targets link dev-dependencies, so this keeps the
  feature out of non-bench builds. Rationale: RFC 0001 requires an isolated
  measurement that reuses an already-constructed view, and no such seam exists.
  The `testing` feature is already a documented test-support surface, so the
  addition is consistent with its purpose, and `#[doc(hidden)]` keeps it out of
  the documented API. It is still a public item, so Q1 asks for confirmation;
  if declined, level 1 is recorded as unmeasurable and the level-2 gate alone
  decides. Date/Author: 2026-11-24, planning agent.
- D8. Decision: the differential suite adds a test-local naive oracle written
  directly from the distance definition, independent of
  `kernels::euclidean_distance_query_points_scalar`. Rationale: the kernel's
  scalar remainder will share the scalar kernel's per-index helper, so an
  oracle that delegates to that kernel would not be independent for the
  remainder path. The existing `DistanceSemantics::oracle_query_points` remains
  for the current backends. Date/Author: 2026-11-24, planning agent.
- D9. Decision: no Verus proof. Bounded model checking plus property tests carry
  the obligations. Rationale: see `Verification plan`,
  `Formal verification decision`. Date/Author: 2026-11-24, planning agent.
- D10. Decision: `insta` snapshots are not used; `rstest-bdd` is not added to
  the dense crate. Rationale: no multivariant output format changes, and adding
  `rstest-bdd` would be an unauthorized dev-dependency in a crate with no
  behavioural suite. The proposed acceptance scenarios are expressed as named
  `rstest` cases instead. Date/Author: 2026-11-24, planning agent.
- D11. Decision: adoption is decided by `RULE-PROD` — deleted production lines
  must be at least added production lines, plus a 10% reduction in the
  arithmetic-body subset — while tests, proofs, the benchmark seam, and
  manifest lines are reported separately under `REPORT-COST`. Rationale: the
  first draft counted tests and proofs inside the net-reduction gate. Measured,
  that rule cannot pass in any configuration: the only deletable body on this
  host is 14 lines, and the structurally necessary additions exceed 300. A gate
  that cannot pass decides the outcome before any work is done, which is the
  opposite of a pre-registered measurement. This revision narrows the gate to
  the question RFC 0001 actually asks — does the consolidation reduce
  maintained production surface — and keeps the evidence cost visible without
  letting it veto the design. Needs maintainer confirmation at approval,
  because it reinterprets T1's "including … test, and proof code". Date/Author:
  2026-11-24, planning agent, after expert-panel review.
- D13. Decision: keep the experiment in the plan, with an explicitly expected
  null result on this host, rather than declining it at the outset. Rationale:
  `RULE-PROD` cannot pass with AVX2-only substitution, so a reader could
  reasonably ask why EP-M2 and EP-M3 exist. Two reasons. First, the RFC
  requires an evaluation, and a recorded measured null result with parity
  evidence is a stronger artefact than an argument from line counts. Second,
  EP-M2's differential suite and the level-2 benchmark are independently useful
  and are retained even under D12. The counter-argument — that this spends
  effort to confirm arithmetic — is exactly Q5, and the maintainer may decline
  EP-M2 onward at approval. Date/Author: 2026-11-24, planning agent, after
  expert-panel review.
- D14. Decision: adopt `main`'s feature-surface discipline from `d6fdbe3`, and
  treat the absence of a public `fearless_simd` feature as load-bearing rather
  than incidental. Rationale: `d6fdbe3` removed the no-op `skeleton` feature
  before the first crates.io release precisely because "once published,
  deleting a feature is a breaking change for any manifest that names it". A
  `fearless_simd` feature added for an experiment that may end in a null result
  would create the same permanent commitment, so Constraint 2's `dep:`-only
  activation is now justified by the repository's own stated policy rather than
  by taste. Two consequences follow. First, the rejection path in D12 stays
  cheap: it can delete `dep:fearless_simd` without a breaking change, which it
  could not do if a public feature existed. Second, EP-M3's `--all-features`
  matrix now enables one fewer feature than it did when written, so that step
  re-derives the set from the manifest rather than copying a list. Date/Author:
  2026-11-24, planning agent, on rebase onto `d6fdbe3`.
- D12. Decision: a null result retains the level-2 benchmark target, the noise
  study, the protocol record, and the documentation update; it removes the
  dependency, the generic kernel, the invocation wiring, the testing seam, the
  level-1 benchmark group, and the kernel proof harness. Rationale: RFC 0001
  forbids leaving an unused backend or trial dependency, but the complete-batch
  benchmark and the noise study are independently useful and fill an identified
  gap. The rejected alternative — reverting everything — would discard the only
  dense distance measurement in the repository. Date/Author: 2026-11-24,
  planning agent.

## Context and orientation

### Terms

- **HNSW**: Hierarchical Navigable Small World, the approximate
  nearest-neighbour graph chutoro builds.
- **SoA**: Structure of Arrays. Coordinates are stored one dimension at a time,
  so every point's value for one dimension is contiguous.
- **Kani**: a bounded model checker for Rust. `cargo kani` explores every
  execution within stated unwind and input bounds.
- **Verus**: a deductive verifier for Rust used in this repository for unbounded
  proofs over pure functions.
- **Gate**: a pre-registered measurement whose outcome decides whether work
  continues. A failed gate is a recorded result, not an error.

### Current control flow

The public path is `DataSource::batch_distances` in
`chutoro-core/src/datasource/mod.rs:241-257`, which becomes
`DenseMatrixProvider::distance_batch` at
`chutoro-providers/dense/src/provider.rs:165`. That calls
`euclidean_distance_batch_pairs` (`simd/mod.rs:52`), which:

1. rejects a length mismatch with `DataSourceError::OutputLengthMismatch`
   (`simd/mod.rs:57-62`);
2. detects a shared query on either side (`shared_query_candidates`,
   `simd/mod.rs:179`);
3. packs when the backend is not scalar, the dimension is non-zero, and there
   are at least two candidates (`should_pack_query_points_for_backend`,
   `simd/mod.rs:148-154`);
4. validates pairs in input order before packing
   (`validate_pairs_in_order`, `simd/mod.rs:157`);
5. builds `DensePointView::from_row_indices` (`simd/mod.rs:102`,
   `point_view.rs:89`) and calls `euclidean_distance_query_points`
   (`simd/mod.rs:126`);
6. collects every result before writing the caller's buffer, which preserves
   output atomicity on error (`simd/mod.rs:64-70`).

`kernels::euclidean_distance_query_points` (`kernels/mod.rs:212`) asserts both
lengths, resolves the cached query function pointer once
(`EUCLIDEAN_QUERY_POINTS_KERNEL.get_or_init`, `kernels/mod.rs:219`), and calls
it. That cache is a bare `fn` pointer (`kernels/mod.rs:42`), which cannot carry
a capability token — the premise of RFC 0001's invocation-enum design.

`dispatch::euclidean_backend` (`dispatch.rs:88`) caches
`choose_euclidean_backend(compiled_simd_support(), runtime_simd_support())`
(`dispatch.rs:153`) in a third `OnceLock` (`dispatch.rs:82`). Eligibility is
`compiled && runtime` per backend (`dispatch.rs:177`); priority is AVX-512,
AVX2, NEON, portable SIMD, scalar (`dispatch.rs:6-11`).

## Verification plan

Verification is co-designed with the implementation. The obligations below are
stated before the kernel is designed, so that the design is shaped by what must
be shown rather than the reverse.

### Abstract model

Let the query be `q = (q_0, ..., q_{d-1})` in `f32`, and the candidates
`p_0, ..., p_{n-1}` with `p_i = (p_i[0], ..., p_i[d-1])`. Let

```plaintext
P = n.next_multiple_of(16)                 padding unit, 16
B_k = [p_0[k], ..., p_{P-1}[k]]            coordinate block for dimension k
                                           with p_j[k] = 0 for j >= n
```

`B_k` is exactly `P` elements long and 64-byte aligned. The reference
computation is

```plaintext
S_i = sum over k = 0..d-1, in increasing k order, of (q_k - p_i[k])^2
R_i = let v = sqrt(S_i) in if v is finite then v else NaN
```

where each subtraction, multiplication and addition is one IEEE-754 binary32
operation with round-to-nearest-even, and the accumulation is strictly
left-to-right. The candidate kernel must satisfy: for every `i` in `0..n`,
`out[i]` is exactly `R_i` as computed by the reference, and `out` has no other
written element.

Preconditions: `q.len() == d`; `out.len() == n`; every `B_k` is `P` elements
long; `P` is a multiple of 16; the packed base is 64-byte aligned. Violating a
precondition is a programming error caught by the existing `assert_eq!` at the
safe boundary (`kernels/mod.rs:217-218`), not a recoverable error.

Malformed input (a length mismatch) is rejected before the kernel by the
existing checks, and the caller's buffer is not modified.

### Invariants and lemmas

Invariants:

- `INV-visible-output` — for `i` in `0..n`, `out[i]` is written exactly once
  with `R_i`; no other element of `out` is written. Covers REQ-F1, REQ-F3.
- `INV-padding-inert` — lanes whose index is at least `n` are never written and
  never influence a written value. Covers REQ-T3.
- `INV-full-chunk-in-bounds` — every full-width read covers exactly
  `L = S::f32s::LEN` contiguous elements starting at a multiple of `L`, and
  `start + L <= P`. Covers REQ-T3.
- `INV-partition` — fix `L` and `P = n.next_multiple_of(16)`. Let
  `S = {0, L, 2L, ...}` be the chunk starts admitted by `start + L <= P`, and
  `start = L * floor(P / L)` the value at loop exit. Then:
  1. the chunk ranges `[s, s + L)` for `s` in `S` are pairwise disjoint and
     their union is `[0, start)`;
  2. the remainder range is `[min(start, n), n)`, empty exactly when
     `start >= n`;
  3. every index in `0..n` is **written exactly once**: by the chunk containing
     it when `i < start`, otherwise by the remainder;
  4. indices in `[n, start)` are *read* by chunks and must never be written.

  `start + L <= P` bounds a read against the *padded* block, not against the
  logical range, so a chunk may legitimately straddle `n`; clause 3 is what
  keeps that safe. Corollary: when `L` divides 16, `start = P >= n`, so the
  remainder is empty for every `n` and clause 2's non-empty branch is
  unreachable on every backend this plan enables. Covers REQ-T3.
- `INV-dimension-order` — per lane, the operations are, in order for each `k`:
  one subtraction `q_k - p[k]`, one multiplication of the delta by itself, one
  addition into the accumulator; no horizontal reduction inside the loop and no
  reordering across `k`. Covers REQ-F2.
- `INV-no-contraction` — the multiply and the add are not fused. Covers
  REQ-F2.
- `INV-single-finalize` — `finalize_distance` is applied exactly once per
  visible index, after the last dimension. Covers REQ-F3.
- `INV-token-provenance` — every token used to execute code came from
  `Level::new()`/`try_detect()` plus `as_avx2`/`as_avx512`/`as_neon`; no
  `assume_supported`, no `dispatch!`, no synthetic mask. Covers REQ-T2.
- `INV-selector-authority` — the generic kernel runs only when
  `dispatch::euclidean_backend()` already selected that backend and the
  pre-registered evidence set contains it. Covers REQ-F4, REQ-T5.
- `INV-no-allocation` — the kernel performs no heap allocation. Covers REQ-T4.
- `INV-pairwise-unchanged` — `EUCLIDEAN_KERNEL`, `squared_l2_tail`, and the
  pairwise branch of `euclidean_distance_batch_pairs` are byte-identical to the
  base revision. Covers REQ-F5.

Lemmas required to connect the invariants to the required behaviour:

- `L-pad-multiple` — `P = n.next_multiple_of(16)` is a multiple of 16, and
  `n <= P`. Source: `point_view.rs:175-177`, `MAX_SIMD_LANES = 16`.
- `L-block-length` — `coordinate_block(k).len() == P` for every
  `k < d`. Source: `PackedSoaStorage::block` (`point_view.rs:61-65`).
- `L-chunk-partition` — for the loop `start = 0; while start + L <= P`, the
  chunk ranges `[start, start + L)` are pairwise disjoint, and after the loop
  `start = L * floor(P / L)`, that is, the largest multiple of `L` not exceeding
  `P`. Two consequences follow, and the plan needs the second, not the first:
  1. `start >= P - L + 1`, so no further full chunk fits.
  2. The remainder must be `[start, n)`, **clamped to `n`**: `min(start, n)` to
     `n`. Because `P >= n`, `start` can exceed `n` (for example `n = 17`,
     `P = 32`, `L = 16` gives `start = 32`), in which case the remainder is
     empty and no index remains. A kernel that blindly iterates `start..n`
     would underflow or panic; one that iterates `min(start, n)..n` is correct
     for every `L` and every `n <= P`.
- `L-visible-count` — for a chunk at `start`, the number of logical points in it
  is `n.saturating_sub(start).min(L)`, which is `0` when `start >= n`.
- `L-lane-arithmetic` — a lane's vector expression computes the same binary32
  value as the scalar expression for the same index and the same `k` order,
  because both perform the same single-rounding operations in the same order.
- `L-finalize` — applying `finalize_distance` once after the last dimension
  yields `R_i`, matching the scalar kernel's post-loop pass
  (`kernels/mod.rs:253-255`).

### Axioms (trusted, not verified here)

- `AXIOM-ieee-lane` — Fearless SIMD's `Sub`, `Mul`, and `Add` on `f32` lanes are
  each a single IEEE-754 binary32 operation with round-to-nearest-even, applied
  lane-wise, with no reassociation and no reduction. Source: `SimdBase` and
  `SimdFloat` documentation, and the absence of any fast-math mode in Rust.
  Depended on by `L-lane-arithmetic`.
- `AXIOM-no-contraction` — the Rust compiler does not contract a separate
  multiply and add into a fused multiply-add for this code. Source: Rust's
  documented floating-point semantics; contracting requires an explicit
  `mul_add`. Corroborated by disassembly evidence in EP-M2, not proved.
- `AXIOM-token-soundness` — a token obtained from `Level`'s safe conversion
  proves the running CPU supports the matching instruction set, and executing
  code compiled for that token is sound. Source: Fearless SIMD's documented
  capability contract. Not verified here; the plan never fabricates a token.
- `AXIOM-chunks-order` — slice iteration (`chunks_mut`, `iter_mut`, `get`)
  yields elements in increasing index order. Source: the standard library.
- `AXIOM-oracle-order` — `euclidean_distance_query_points_scalar` accumulates in
  increasing dimension order and is unchanged by this work. Source: the file's
  current text, guarded by `INV-pairwise-unchanged`'s companion check that the
  scalar kernel's lines are untouched (Constraint 4).
- `AXIOM-avx2-host` — this development host executes x86-64-v3. Source: measured
  `/proc/cpuinfo` flags (`avx`, `avx2`, `fma`, `bmi1`, `bmi2`, `f16c`, `movbe`,
  `abm`, `cx16`, `popcnt`, `sse4_2`, `xsave`), recorded in
  `Artefacts and notes`. Exercised by every AVX2 test run.

### Formal verification decision

No Verus proof is planned. The obligations that matter here are (a) bounded
index arithmetic over small integers with a stride, and (b) an equality between
a vector expression and a scalar expression under IEEE-754. Obligation (a) is
exactly the shape bounded model checking handles better than a deductive proof:
Kani explores every admissible `n`, `d`, and `L` within stated bounds, and the
existing 2.2.7 harnesses establish that this is tractable in this crate.
Obligation (b) cannot be established by a Rust-level proof at all, because it
depends on `AXIOM-ieee-lane` and `AXIOM-no-contraction`, which describe the
library and the code generator rather than chutoro's own logic; a Verus proof
would either assume them or restate them. The repository's Verus proofs
(`verus/edge_harvest_proofs.rs`, `verus/session_core_distance.rs`) cover
contractual business logic over unbounded inputs, which this change does not
introduce: the distance contract is unchanged and the scalar oracle is
untouched. The dispatch policy is a total function over finite domains, where
exhaustive enumeration is strictly stronger than a proof. Recorded as D9.

Residual gap: Kani does not model Fearless SIMD's vectors, and no harness
claims to. The harnesses prove chutoro's own index arithmetic and policy only.

### Suggested BDD features

The dense crate has no `rstest-bdd` runner, and adding one would be an
unauthorized dev-dependency, so no feature file is added (D10). The observable
acceptance behaviour is expressed as named `rstest` cases instead. The proposed
wording, for the design update and for reviewers, is:

```gherkin
Feature: Dense query-to-points distance is unchanged by the kernel substitution
  Scenario: A shared-query batch returns the same distances
    Given a dense matrix whose rows 1 to 33 are candidates for row 0
    When the provider scores row 0 against those candidates
    Then each returned distance matches the scalar reference within 1.0e-5
    And the result count equals the candidate count

  Scenario: A non-finite candidate is reported as NaN
    Given a query containing positive infinity
    When the provider scores it against a finite candidate
    Then the returned distance is NaN

  Scenario: Padding lanes are computed but never become results
    Given 17 candidates, so the packed block holds 32 lanes
    And a query containing positive infinity
    When the provider scores them
    Then the 17 visible distances are all NaN
    And no result is produced for lanes 17 to 31
```

Mapping: the first scenario is
`simd::tests::fearless::naive_oracle_parity_over_counts_and_dimensions`; the
second is `simd::tests::fearless::non_finite_canonicalization`; the third is

## Performance experiment and preregistration

This section is committed before any candidate code and before any candidate
timing. It is the pre-registration RFC 0001 requires. Changing it after a
measurement requires a dated `Revision note` entry and a `Decision log` entry
naming the reason.

### Inputs and matrix

### Instrument and protocol

- Instrument: Criterion 0.5.1 through a new `dense_distance` target in
  `chutoro-benches`, `harness = false`, registered in
  `chutoro-benches/Cargo.toml`.
- Corroboration: `hyperfine` 1.20.0 through a new
  `scripts/bench-dense-distance.sh`, built like
  `scripts/bench-neighbour-scoring.sh:22-46`: one
  `cargo bench -p chutoro-benches --bench dense_distance --no-run --message-format=json`
  per arm, with `jq` extracting `.target.name == "dense_distance"`, and a
  separate `CARGO_TARGET_DIR` per arm so the two executables do not overwrite
  each other. Treat `hyperfine` as a **smoke check only**; Criterion and cycle
  counts are the primary signal, per `docs/developers-guide.md:2934-2935`.

  **Do not use `--profile-time` for a decision.** Criterion's profile mode
  computes `iterations = remaining / mean_exec_time` and runs exactly enough
  iterations to fill a fixed budget, so the process takes about 2 s whether the
  kernel is 10% faster or 10% slower; it cannot corroborate a direction. The
  existing helper script uses it precisely because it is a smoke check. For a
  directional measurement the script must run a fixed iteration count, so wall
  time is proportional to throughput.

- Pairing: RFC 0001 requires paired, interleaved measurements, and `hyperfine`
  does **not** interleave — with two commands and three runs it executes
  `A A A B B B`. Alternation must be driven explicitly, one round at a time,
  and aggregated by per-round ratio:

  ```sh
  for round in 1 2 3 4 5; do
    taskset -c 4-7 hyperfine --warmup 0 --runs 1 \
      --export-json "/tmp/dd-$round.json" "$BASELINE" "$CANDIDATE"
  done
  jq -s 'map(.results[1].mean / .results[0].mean) | sort | .[length/2|floor]' /tmp/dd-*.json
  ```

  Report the median and the full set of five per-round ratios. Pin the round
  count at five and the aggregation rule here, so the statistic is not chosen
  after seeing it. `taskset` narrows scheduling; it does **not** isolate these
  cores from other agents, so the noise study below decides whether the
  instrument is usable at all.

- Use a positional Criterion filter, not `--exact`: this repository intercepts
  the literal `--exact` flag to mean a bounded probe
  (`is_exact_benchmark_probe_args`,
  `chutoro-benches/src/criterion_support.rs:60-69`), and several targets switch
  to reduced sizes or no-op registration when they see it. Criterion applies a
  positional filter *after* fixture construction, so register filtered cases
  cheaply or accept the setup cost.
- Criterion comparison across two worktrees: Criterion's output directory is
  per worktree (`$CARGO_TARGET_DIR/criterion`, else `./target/criterion`), and
  `--baseline` panics when the named baseline is absent. Copy the baseline
  across, exactly as the repository's own CI does
  (`.github/workflows/benchmark-regressions.yml:184-192`), and pass `--noplot`
  to match CI:

  ```sh
  # In the baseline worktree:
  cargo bench -p chutoro-benches --bench dense_distance -- \
    --save-baseline reference --noplot
  # Copy reference/ into the candidate worktree's target/criterion, then:
  cargo bench -p chutoro-benches --bench dense_distance -- \
    --baseline reference --noplot
  ```

  Define the baseline worktree as the EP-M1 commit: it contains the complete
  benchmark target and the seam-free level-2 path, and it is the only revision
  that is comparable without containing the candidate kernel. Never compare
  against a stored baseline from another day.
- Level 1 needs its own mechanism, because the packed group exists only after
  the seam is added and Criterion compares per benchmark id, so `packed/legacy`
  can never be the baseline for `packed/fearless`. Select the variant by an
  environment variable so the **same** id is registered in both runs; save the
  legacy run as the baseline and compare the fearless run against it, in two
  processes. The level-1 baseline revision is therefore the EP-M2 commit that
  adds the seam, not the EP-M1 commit.
- Fixed inputs: reuse the existing seed constant
  (`BENCH_SEED = 0xC4A7_0203_0000_0231`,
  `chutoro-benches/src/neighbour_scoring/benchmark_support.rs:28`) or state
  that the new target defines its own; either way, generate every value
  deterministically so both arms measure identical data.
- Dimension 0 cannot be built through the `neighbour_scoring` fixture pattern:
  Arrow collapses a zero-width `FixedSizeListArray` to zero rows, so the
  provider reports `OutOfBounds` before any kernel runs. Either construct the
  provider with a zero-width-but-nonzero-length array, or record dimension 0 as
  unmeasurable. Do not silently drop it.
- Release builds, warmed caches, one thread (the kernel is single-threaded;
  `RAYON_NUM_THREADS` is pinned anyway so a future parallel caller cannot
  confound the comparison).
- Separate initialization from steady state: construction of the packed view and
  the output buffer happens outside the timed closure at level 1.
- Record with every result: host model, `rustc --version`, resolved
  `fearless_simd` version, enabled Cargo features, the selected backend, and
  the measured token availability.

### Noise establishment

Before any candidate timing, run five unchanged-versus-unchanged Criterion
comparisons at each gated cell on the base revision. A cell's instrument passes
only if **both** of these hold, where `limit` is that cell's Table 5 tolerance:

1. **Spread.** The 95% confidence interval half-width of every A/A comparison is
   at most `min(1.0%, limit / 2)`.
2. **Drift.** The *point estimate* of every A/A comparison lies within
   `±min(1.0%, limit / 2)`.

Tying the allowance to the cell's own limit is what stops a noisy cell from
passing the noise check while being unable to decide the gate: a cell whose
half-width were 5% could never resolve a 3% limit, so admitting it only defers
an inconclusive verdict. The drift condition is the one that matters on this
host: Criterion's change interval is bootstrapped from a single pair of runs,
so a systematic shift between the two blocks — a frequency or neighbour change
— moves the point estimate while leaving the interval narrow. A rule that
checked only half-widths would certify a biased instrument as precise.

Report all five point estimates and all five half-widths per cell, not only the
intervals.

Rationale for allowing anything above 1.0%: Criterion amortizes timer
resolution by batching many iterations per sample, so quantization is not the
constraint. The real limits are per-iteration harness overhead folded into the
measured mean, and drift on a host shared with other agents' builds. The
allowance is therefore an overhead allowance, capped by the gate it protects.

Sizing and the gated set: see the single table in `Decision tolerances`. Cells
whose measured time is under 2 ns are reported as unmeasurable rather than
gated; that is a recorded limit of the instrument, not a pass.

Level-1 cells need their own A/A study, run after the EP-M2 seam exists (legacy
variant against legacy variant), because the packed group does not exist during
EP-M1. A packed cell without an A/A study is reported, not gated.

If a cell fails after one tightening pass (higher sample size, longer
measurement time, pinned cores), the experiment is inconclusive at that cell
and is recorded with the observed half-width and point estimates rather than
being accepted as equivalent.

### Decision tolerances

This table is the single definition of which cells are gated. No other section
may restate or extend it. The upper bound of the 95% confidence interval of the
relative change, candidate against baseline, must be within the stated limit.

Dimensions are `32`, `128`, and `768` unless a row says otherwise. Those three
are the dimensions the existing `neighbour_scoring` plan already measures
(`chutoro-benches/src/neighbour_scoring/benchmark_plan.rs:9`), so a conclusion
here speaks to a workload callers actually run.

| Level  | Candidates         | Dimensions   | Limit                            |
| ------ | ------------------ | ------------ | -------------------------------- |
| batch  | 8                  | 32, 128, 768 | +5.0%                            |
| batch  | 16, 24, 32, 48     | 32, 128, 768 | +3.0%                            |
| batch  | 64, 128, 256, 1024 | 32, 128, 768 | +2.0%                            |
| packed | 16, 32, 64, 128    | 32, 128, 768 | +3.0%                            |
| either | 0, 1               | any          | control: no gate, report only    |
| either | any                | 0            | control: no gate, report only    |
| either | 2, 4               | any          | diagnostic: no gate, report only |
| either | any                | 1, 8, 16     | diagnostic: no gate, report only |

*Table 5: The pre-registered gated set and limits. Limits are one-sided: any
improvement is acceptable, and no speed-up is required.*

Why some classes are reported but not gated:

- Candidates 0 and 1, and every dimension-0 cell, never enter the packed kernel:
  `should_pack_query_points_for_backend` requires
  `dimension > 0 && candidate_count > 1`
  (`chutoro-providers/dense/src/simd/mod.rs:148-154`). Gating them would fail
  the plan for a change the kernel cannot cause. They are scope-drift
  *controls*: a measurable change means something outside the kernel moved,
  which is reported and investigated rather than scored.
- Candidates 2 and 4 are ungated because one native vector covers them at every
  width, so the cell measures dispatch and call overhead rather than
  arithmetic. Still reported, because a dispatch regression would show there
  first.
- Dimensions 1, 8, and 16 are diagnostic. On this host's 8-lane AVX2 token they
  execute at most two vector chunks, so any honest half-width is a large
  fraction of the measurement; gating them would decide the experiment on
  instrument error. They are measured and reported because they expose a
  remainder bug immediately.

Rules:

1. Adoption requires every gated cell of Table 5 to be within its limit, on the
   same host in the same session, with the `Noise establishment` conditions
   satisfied for that cell.
2. A packed-kernel regression must be reported even when the complete-batch
   number hides it.
3. No pipeline benefit may be claimed from any of these measurements, and no
   end-to-end speed-up is required for adoption.
4. An interval that straddles a limit, or a cell whose noise evidence fails
   `Noise establishment`, is inconclusive rather than a pass.
5. A diagnostic or control cell that moves outside its own noise band is
   reported as drift and investigated before the gate result is accepted, even
   though it is not scored.

### Measurement budget

The full Table 4 matrix is far larger than the gated set and would not fit the
per-milestone time tolerance. Pre-register the cost:

- Gate only the Table 5 cells. Measure the remaining matrix cells once, at
  reduced cost, for the record.
- Use explicit
  `--warm-up-time 1 --measurement-time 2 --sample-size 30 --noplot` for every
  recording run. Criterion's defaults (3 s warm-up, 5 s measurement, 100
  samples) cost at least 8 s per cell and are not affordable across the matrix.
- Budget: one full gated run is expected under 10 minutes at these settings;
  the five-round A/A study is under 50 minutes per level. If a milestone's
  measurement work exceeds two hours of wall clock, stop and record the reduced
  matrix actually measured rather than silently extending the milestone.

## Maintenance accounting

RFC 0001 requirement T1 makes the maintenance reduction the deciding gate. Its
arithmetic is pre-registered here, and it is stated so that it *can* pass. A
gate that cannot pass is not a gate; it is a foregone conclusion that wastes
the measurement work, so the first draft's single net-reduction rule is
replaced by two separately reported quantities and one bounded production rule.

### Measured starting surface

Non-blank, non-comment lines at `2c89752`, counted with

| ------------------------------------------------ | ----- | ----------------------------------------- |
| x86 query macro body (`x86_simd.rs:56-106`)      | 46    | Only if both x86 backends are substituted |
| AVX-512 instantiation (`x86_simd.rs:130-144`)    | 14    | Only with AVX-512 execution evidence      |
| AVX2 instantiation (`x86_simd.rs:168-182`)       | 14    | Yes, with AVX2 evidence                   |

| Portable-SIMD query (`portable_simd.rs:31-61`)   | 29    | Never (Constraint 5)                      |

*Table 6: The deletable surface, measured. Under D6's AVX2-only substitution
the removable total is 14 lines; with every backend substituted it is 107.*

### Production rule (`RULE-PROD`)

The deciding gate, and the only one that can fail the experiment:

- `PROD_DELTA` = deleted production lines in
  `chutoro-providers/dense/src/simd/**`, counting arithmetic bodies, dispatch,
  and `cfg` gates, and excluding tests, proofs, and documentation.
- `PROD_ADD` = added production lines in the same scope, counting the generic
  kernel, the token and invocation types, the policy function, the cached
  static, and the selection match.
- Adoption requires `PROD_DELTA >= PROD_ADD` **and** a recorded net reduction
  of at least 10% in the *arithmetic-body* subset alone (the six rows of Table
  6). The second clause prevents a patch that deletes one body and adds ninety
  lines of dispatch from claiming a consolidation.

This rule is satisfiable and is not trivially satisfied. Under AVX2-only
substitution, `PROD_DELTA = 14`, so `PROD_ADD` must stay at or below 14 lines —
which no honest token-carrying implementation of this design reaches. **The
expected outcome on this host is therefore a null result, and the plan says so
in advance** rather than discovering it after the measurement work. That is the
faithful reading of RFC 0001: it explicitly contemplates that "preserving every
legacy body while adding the generic body can increase both implementation
count and maintenance cost. Record a null result if the complete patch cannot
demonstrate a useful net reduction."

`RULE-PROD` can pass only if Q2 supplies AVX-512 and AArch64 execution, or Q3
permits deleting bodies whose only role is a weak-capability fallback. Both are
maintainer decisions, and Q5 asks whether the experiment should proceed at all
on an AVX2-only host given this arithmetic.

### Reported cost (`REPORT-COST`)

Tests, proofs, benchmark seam, and manifest lines are counted and reported but
are **not** part of `RULE-PROD`, because they are the price of the evidence
rather than maintained runtime surface, and because charging them to the gate
would guarantee failure regardless of design quality:

- the differential suite, the policy enumeration, and the partition harness;
- the `testing`-gated seam and the new benchmark group;
- the manifest and lockfile lines.


### Why this replaces the single net-reduction rule

The first draft required a 10% net reduction in a surface that included the new
tests and proofs. Measured against the 14 deletable lines above, and the
structurally necessary 300-plus added lines of kernel, dispatch, tests, and
proofs, no base count makes that rule pass. It was recorded as "very likely a
null result"; it was in fact a certain one. A pre-registered gate that cannot
pass is worse than no gate, because it conceals that the design decision was
already made. `RULE-PROD` is the narrowest rule that still answers RFC 0001's
question — *does the consolidation reduce maintained production surface?* —
while keeping the evidence cost visible and out of the verdict.

different expiries look similar and only one is dismissible:

| Signal                                        | Where it appears               | Meaning                                                            | Action                                                                                        |
| --------------------------------------------- | ------------------------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `[build-limits] … waiting for a compile slot` | stderr, during the build       | Admission queueing                                                 | Normal. Wait.                                                                                 |

not admission. Triage a slow harness against the verification-cost tolerance

What this establishes, and what it does not:

- **Establishes** that the proposed lane-per-candidate shape compiles against
  the real 1.2 API, that `S::f32s::LEN` is 8 on this host's token, and that the
  vector expression reproduces the scalar per-index expression **bit for bit**,
  including every tail class in the matrix. `AXIOM-no-contraction` therefore
  held in this build, which is corroborating evidence, not a proof.
- **Does not establish** anything about production dispatch, the packed
  `DensePointView` blocks, AVX-512, NEON, or performance. The probe used plain
  `&[f32]` blocks, a debug build, and no Criterion measurement, so no timing
  claim of any kind follows from it.
- The probe's first draft failed to compile because it passed a `Level` where a
  `<S: Simd>` was required, producing the `Level: Simd` diagnostic recorded
  above. That is why `FearlessToken` is required rather than optional.

Library contract evidence, from docs.rs and crates.io on 2026-11-24:

```plaintext
fearless_simd 1.2.0        released 2026-10-25  rust_version 1.89
fearless_simd_macros 0.1.0 released 2026-09-21  rust_version 1.89
Level::{new, try_detect, as_avx2, as_avx512, as_neon, is_fallback, baseline}

SimdBase::from_slice: "The slice must be exactly the size of the SIMD vector."
SimdBase::store_slice: "The slice must be exactly the size of the SIMD vector."
```

Consequence: loads and stores are exact-width and panic on a length mismatch, so
`INV-full-chunk-in-bounds` is a safety precondition, not a convenience.

`Level` is **not** a `Simd` token. Verified by compiler diagnostics on
2026-11-24 from a scratch crate: calling a `<S: Simd>` function with a `Level`
value is rejected with
`the trait bound fearless_simd::Level: fearless_simd::Simd is not satisfied`,
and the compiler names `Avx2`, `Avx512`, `Sse2`, and `Sse4_2` as the types that
do implement it. Consequences:

- The generic kernel must be instantiated per concrete token, so
  `FearlessToken`'s variant set is not a convenience but the only route to the
  kernel. `Level` is a selector, not an executor.
- `vectorize` is a `Simd` method, so there is no token-generic entry point: the
  match on `Level` must happen before the call, once per batch.
- `Level::baseline()` can return `Sse2` on x86-64, a backend this plan does not
  substitute, so `baseline()` must never be used to obtain a kernel token.

Expected implementation results, to be replaced with real transcripts as each
milestone completes: noise half-widths, packed and batch gate tables, the
disassembly excerpt, the maintenance counts, and the executed-versus-skipped
backend table.

```sh
  | grep -c 'fearless_simd v'                  # expect 1
cargo tree -p chutoro-providers-dense --all-features -e normal --locked \
  | grep -c 'fearless_simd v'                  # expect 1
```

`-e normal` excludes build and dev edges, which matters now that two
dev-dependencies are added. `grep -c` exits 1 on zero matches, so the two
"expect 0" cases need `|| true` under the repository's `pipefail` convention;
record the printed count rather than relying on the exit status.

`dep:` creates no implicit feature: the only public features remain `simd_avx2`,
`simd_avx512`, `simd_neon`, `nightly_portable_simd`, and `testing`. Verified
on 2026-11-24 with a scratch crate: `cargo metadata` reports exactly the
declared feature map, and `cargo tree --no-default-features -e normal` lists no
optional dependency.

**Partial-feature coverage hazard.** Attaching `dep:fearless_simd` to all three
native features means a build with only `simd_avx512` or only `simd_neon`
compiles the dependency on a machine that may have neither instruction set. The
dependency is then unused-but-linked for that target, which is harmless for
correctness and required for the kernel to exist when the token is available,
but it does mean the level-1 benchmark must report which backend actually ran
rather than which feature was enabled. EP-M3's feature-matrix table records
both.

**Architecture coverage.** The kernel module is generic over `S: Simd` and
names no token type, so it compiles on every target whenever a native feature
is enabled. Only the `FearlessToken` variants are architecture-gated, and the
NEON variant is **AArch64-only**, because `fearless_simd` 1.2 defines `Neon`
only under `target_arch = "aarch64"` (`generated.rs:50-51,69-70`;
`Level::as_neon` at `lib.rs:524`). A 32-bit `arm` build compiles the legacy
NEON body and never the generic kernel: that is a capability exception under
REQ-T1, not an oversight.

## Open questions for the maintainer

These need answers before or during approval because they change what the plan
does. The plan's default is stated for each.

- **Q1. The level-1 measurement seam.** RFC 0001 requires an isolated
  packed-kernel benchmark, but `DensePointView` is `pub(crate)` and the kernel
  entry is private, so `chutoro-benches` cannot reach them. D7 proposes a
  `#[cfg(feature = "testing")]`, `#[doc(hidden)]` fixture in the dense crate.
  That is a new public item, behind a non-default test-support feature, and the
  RFC forbids a new public abstraction. Default if declined: level 1 is
  recorded as unmeasurable and only the complete-batch gate decides.
- **Q2. Execution hosts.** RFC 0001 T5 requires native execution before a
  backend is substituted, and this host has neither AVX-512 nor AArch64.
  Default: AVX2-only substitution, with AVX-512 and NEON reported as compiled,
  selected, and not executed. If an Ice Lake-class and an AArch64 host can be
  provided, the plan gains two more substitution candidates and `RULE-PROD`
  changes from unsatisfiable to plausible. It does not become easy: with all
  three substituted the deletable total is 107 lines against an estimated
  `PROD_ADD` of 60 to 120, so the outcome is genuinely open rather than certain.
- **Q3. Retaining the AVX2 legacy body.** RFC 0001 requires a missing token to
  fall back to the legacy body the selector chose, so the AVX2 body stays and
  `RULE-PROD` fails on this host. Would the maintainer accept amending that
  rule to allow falling back to the *scalar* oracle when the v3 token is
  absent? Default: no — the RFC rule stands and a null result is recorded. Note
  that this is the single decision that most changes the plan's outcome, so it
  is worth answering explicitly rather than by default.
- **Q4. The `RULE-PROD` thresholds (D11).** `RULE-PROD` requires
  `PROD_DELTA >= PROD_ADD` plus a 10% reduction in the arithmetic-body subset.
  Is that the intended reading of "a useful net reduction", which RFC 0001 also
  qualifies as counting "test, and proof code"? Default: as written, with test
  and proof cost reported separately under `REPORT-COST`.
- **Q5. Whether to run EP-M2 onward at all.** Given Q3's default and the
  14-line deletable surface, `RULE-PROD` cannot pass on this host, so EP-M2 and
  EP-M3 will end in a recorded null result. D13 argues to proceed anyway,
  because a measured null result with parity evidence is a stronger artefact
  than an argument from line counts, and because the differential suite and
  level-2 benchmark are retained either way. The maintainer may instead decline
  EP-M2 onward at approval and treat EP-M1's baseline measurement as the whole
  deliverable. Default: proceed, since the roadmap asks for an evaluation, not
  for an adoption.
- **Q6. The token-provenance contract.** The verification plan adds a
  `tests/workflow_contracts/fearless_token_provenance_test.py` source contract
  so that `assume_supported`, `dispatch!`, `Level::baseline`, and any `unsafe`
  block in the kernel files fail a standing gate rather than depending on
  review. This is new automation in a shared test surface. Default: add it,
  following the `trim_scoring_dispatch_test.py` precedent from ADR 0006.
- **Q7. The allocation test's `unsafe`.** The no-allocation obligation wants a
  counting `#[global_allocator]` in a `#[cfg(test)]` unit test beside the
  kernel, which is the only placement that can reach the private items. A
  global allocator needs a project-owned `unsafe impl GlobalAlloc`, and RFC
  0001 T4 and Constraint 7 forbid new project-owned `unsafe`. Default: allow
  it, scoped to one test module with a `SAFETY` comment, because nextest
  isolates it and it is the only decisive evidence available. The alternative
  is a statement audit, which cannot see allocation inside
  `fearless_simd::vectorize`.

## Out of scope

- Roadmap item 2.3.2 and anything under `chutoro-core/**`.
- Replacing the pairwise kernels, or any change to `squared_l2_tail`.
- Any change to `DensePointView`'s storage, alignment, padding unit, or packing
  policy.
- A public kernel trait, a wrapper crate, or a cross-crate SIMD framework.
- GPU or `wgpu` backends, prefetch policy, buffer-reuse APIs, or new thread
  pools.
- An AArch64 CI runner or an MSRV CI lane. Both are recorded as gaps, not fixed
  here.
- Any change to the 2.3.2 gates or their recorded outcome.
