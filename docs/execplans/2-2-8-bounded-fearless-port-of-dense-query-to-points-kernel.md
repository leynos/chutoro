## Purpose / big picture

Chutoro scores Hierarchical Navigable Small World (HNSW) candidates through one
query-centric distance call. `DataSource::batch_distances(query, candidates)`
reaches `DenseMatrixProvider`, which detects that every pair shares a query
row, packs the candidate rows dimension-major into a 64-byte-aligned padded
block, and runs a packed "query to many points" Euclidean kernel. That kernel
decides how fast neighbour scoring runs.

The dense provider maintains that same coordinate loop five times over: a scalar
reference, an AVX2 body, an AVX-512 body (both generated by one macro), a NEON
body, and a nightly `std::simd` body. The pairwise kernels are a *separate* set
of five, deliberately out of scope here. Fearless SIMD 1.2 offers one safe,
generic vector API whose native width is the hardware's, with no project-owned
`unsafe` and no per-architecture intrinsic spelling. If a single generic body
can replace the query kernels' per-architecture bodies without changing a single
distance, the provider becomes cheaper to maintain.

This plan decides that question by measurement rather than by argument. It has
two outcomes, and both are successful completions:

1. **Adoption.** The generic kernel preserves parity, executes on every backend
   it replaces, keeps complete-batch performance inside a pre-registered
   tolerance, and demonstrably reduces the maintained query-kernel surface. The
   redundant per-architecture query bodies are deleted for the backends that
   have native execution evidence.
2. **Null result.** Any gate fails, or the complete patch (including retained
   legacy bodies, dispatch, tests, and proofs) does not reduce the maintained
   surface. The experiment is reverted, the established path stays, and the
   measured or explicitly inconclusive result is recorded beside roadmap item
   2.2.8.

A caller observes nothing in either case. After the change, and equally after a
null result, this still holds for one query `q` and candidate rows `p_i`:

```rust
let distances = provider.batch_distances(0, &[1, 2, 3])?;
// Element i is the Euclidean distance from row 0 to row 1 + i,
// within the dense provider's established 1.0e-5 absolute tolerance,
// with any non-finite result reported as f32::NAN.
```

Terms used below:

- **Packed layout**: `DensePointView` stores one contiguous coordinate block per
  dimension, each block `padded_point_count` long, where
  `padded_point_count = point_count.next_multiple_of(16)`. Unused lanes hold
  `0.0`. The base pointer is 64-byte aligned.
- **Lane-per-candidate**: each SIMD lane accumulates one candidate point's
  squared differences across all dimensions. This is the existing shape of the
  packed kernel and of the proposed generic kernel.
- **Capability token**: a Fearless SIMD value (`Avx2`, `Avx512`, `Neon`) that
  exists only if the running CPU was proven to support the matching instruction
  set. A token is a proof, not a hint.
- **Legacy body**: a current per-architecture packed query kernel
  (`x86_simd.rs`, `neon_simd.rs`).
- **Invocation**: the cached decision of which implementation answers the next
  query-to-points call, either a token-bearing generic kernel or a legacy
  function pointer.

pipeline-share gates, which were measured separately and failed on 2026-11-23

`2-3-2-vectorize-edge-weight-transforms-and-candidate-filtering` branch).

## Constraints

These are hard invariants. Violating one requires escalation, not a workaround.

1. **No public interface change.** `DataSource`, `DenseMatrixProvider`,
   `PointPair`, `distance`, `distance_batch`, `batch_distances`, the error
   types, and every existing public signature keep their shape and semantics.
   No Fearless SIMD token, vector, or mask appears in any public signature. The
   crate-internal `simd` module stays private
   (`chutoro-providers/dense/src/lib.rs:12`).
2. **No new public Cargo feature.** `fearless_simd` is an optional dependency
   activated only through the existing `simd_avx2`, `simd_avx512`, and
   `simd_neon` features by `dep:` entries, so no implicit `fearless_simd`
   feature is exposed. `--no-default-features` and the nightly
   `nightly_portable_simd`-only configuration must not pull the dependency in.
3. **Preserve the packed layout.** `DensePointView` keeps its 64-byte
   alignment, its 16-point padding unit, its zero fill, and its
   `from_row_indices` allocation policy. This plan does not change
   `point_view.rs` storage, only the compile-time reach of one accessor.
4. **Preserve the scalar reference.** `euclidean_distance_query_points_scalar`
   remains the numerical oracle and keeps its exact expression order.
5. **Preserve feature selection.** The existing selector
   (`dispatch::euclidean_backend`, priority AVX-512, AVX2, NEON, portable SIMD,
   scalar) remains the authority for backend eligibility and order. A Fearless
   kernel runs only where the selector already chose that backend and a safe
   token for it is available.
6. **Preserve the pairwise kernels.** `euclidean_distance`,
   `euclidean_distance_batch_pairs`' pairwise path, `EUCLIDEAN_KERNEL`, and
   `squared_l2_tail` are out of scope and must not change behaviour.
7. **No project-owned `unsafe` in new code.** No `assume_supported`, no
   `kernel!` intrinsic wrapper, no `core::arch` intrinsics, no `unsafe` block
   in the new module or in the new dispatch code.
8. **No unrestricted dispatch.** `fearless_simd::dispatch!` must not be used: it
   can select an instruction set that a Cargo feature has excluded. Tokens come
   only from `Level::new()` or `Level::try_detect()` and the safe
   `as_avx2`/`as_avx512`/`as_neon` conversions.
9. **Calling-thread execution.** The kernel stays synchronous on the caller's
   thread. No Rayon task, no blocking pool operation, no index re-entry. This
   preserves ADR 0006's callback contract under `insert_mutex`.
10. **No new allocation.** The kernel allocates nothing. It writes only the
    caller's output slice.
11. **MSRV 1.89.0.** `Cargo.toml:19` declares it. The dense manifest currently
    does not inherit it (RFC 0001 footnote 8); this plan adds
    `rust-version.workspace = true` to `chutoro-providers/dense/Cargo.toml` so
    the package has effective metadata, as RFC 0001 requires.
12. **Authorized dependencies.** Production: `fearless_simd = "1.2"`, declared
    in
    `[workspace.dependencies]` and consumed only by
    `chutoro-providers-dense` with `optional = true`.
    `fearless_simd_macros = "0.1"` is authorized but is **not** used unless
    Decision D3 is revised. Development: `pretty_assertions = "1.4.1"` and
    `googletest = "0.14.4"`, dev-dependencies of
    `chutoro-providers-dense` only, authorized by the maintainer for this task.
    No other dependency, in any crate, is authorized.
13. **File size.** No source file may exceed 400 lines (`AGENTS.md`).
    `chutoro-providers/dense/src/simd/kernels/mod.rs` is 303 lines and
    `simd/dispatch.rs` is 232, so the new module must be its own file rather
    than an addition to those.
14. **Do not modify** `chutoro-core/**`, `chutoro-providers/text/**`,
    `chutoro-compile-contracts/tests/trybuild/**`, or `verus/**` except where a
    milestone names the file. Task 2.3.2 is out of scope.
15. **Historical documents stay untouched.** Completed ExecPlans, the RFC's and
    ADR's dated sections, and `docs/chutoro-design.md`'s existing dated
    implementation updates are amended only by appending new dated material.

## Risks

- **Risk: no AVX-512 and no AArch64 execution host.** The development host is
  an AMD Ryzen 9 3900 (Zen 2): AVX2 and FMA are present, `avx512f` is absent,
  and no AArch64 runner or cross toolchain is installed. RFC 0001 requirement
  T5 forbids substituting a backend without native execution evidence, so
  AVX-512 and NEON substitutions cannot be enabled from this host. Severity:
  high. Likelihood: certain. Mitigation: pre-register the AVX2-only enablement,
  report executed-versus-skipped backends explicitly in every milestone, and
  treat the maintenance gate as the deciding gate (R2 below).
- **Risk: the maintenance gate cannot pass while legacy bodies are retained.**
  RFC 0001 requires a missing token to fall back to "the same legacy query
  implementation that the existing selector chose", so every legacy body whose
  backend is not fully substituted must stay. With AVX2-only substitution the
  complete patch is very likely a net *increase*. Severity: high. Likelihood:
  high. Mitigation: this is a legitimate null result and is handled as success;
  open question Q3 asks whether deleting the AVX2 legacy body is acceptable,
  and only an explicit maintainer decision can change the rule.
- **Risk: complete-batch cost hides the kernel.** Packing, validation, and
  result transfer dominate small batches; the 2.3.1 profile found realistic
  HNSW buckets fragmented at 8 to 48 candidates. A faster kernel may not move
  the batch number, and an extra dispatch match may cost more than the kernel
  saves at 8 candidates. Severity: medium. Likelihood: medium. Mitigation:
  two-level measurement with separate tolerances, and a pre-registered report
  of packed-kernel regressions even when packing hides them.
- **Risk: compiler contraction changes results.** If LLVM contracts the separate
  multiply and add into a fused multiply-add, results diverge in the last bits
  and the bit-identity test fails. Severity: high. Likelihood: low. Mitigation:
  the reference Rust build does no fast-math and Rust does not contract without
  an explicit `mul_add`; the plan still requires disassembly evidence and a
  bit-identity test that a contracted build would fail.
- **Risk: `Avx2` is not `avx2`.** The token denotes x86-64-v3 (AVX2 plus FMA,
  BMI1, BMI2, F16C, MOVBE, LZCNT), so a CPU or virtual machine that reports
  `avx2` but not the full bundle selects AVX2 yet gets no token and runs the
  legacy body. Severity: low. Likelihood: low. Mitigation: the policy is a pure
  function tested over all token-availability combinations, and the fallback is
  the unchanged legacy body, so the outcome is a missed opportunity rather than
  a regression.
- **Risk: compile time and binary size grow.** Multiversioning and a second
  backend in one crate can increase both. Severity: medium. Likelihood: medium.
  Mitigation: record clean-build time and release binary size before and after;
  record them in `Outcomes & retrospective`; declare a null result if the
  growth is material and the maintenance reduction is not.
- **Risk: `#[simd]` macro cost.** `fearless_simd_macros` pulls procedural-macro
  dependencies into the dense crate for one function. Severity: low.
  Likelihood: low. Mitigation: Decision D3 uses the manual inlining route first
  and adds the macro only if disassembly shows the manual route fails to
  produce packed instructions.
- **Risk: benchmark noise on a shared host.** The host runs other agents'
  builds; load average has been observed above 20. Severity: high. Likelihood:
  high. Mitigation: the noise study in EP-M1 must satisfy the rule in
  `Noise establishment` at every gated size class before any candidate timing is
  accepted; otherwise the cell is inconclusive and recorded as such.
- **Risk: cfg drift in partial feature sets.** The new module's gate, the
  dependency activation, and `DensePointView::padded_point_count`'s existing
  `cfg` list (`point_view.rs:123-139`) must agree, or a partial feature build
  fails to compile.
  Severity: medium. Likelihood: medium. Mitigation: EP-M3 enumerates and builds
  every supported feature combination, and the compile-contract tests are
  extended where a machine-checkable rule exists.
- **Risk: `cargo::unused_dependencies` fires in a partial feature set.** A build
  such as `--no-default-features --features simd_neon` on x86-64 enables
  `fearless_simd` through `dep:` while the kernel module is `cfg`-excluded, so
  the dependency is compiled and never named. Cargo warns, and the gate's
  `RUSTFLAGS=-D warnings` turns that into an error.
  Evidence: the feasibility probe reproduced exactly this warning for an unused
  `fearless_simd_macros` declaration.
  Severity: medium. Likelihood: high. Mitigation: EP-M3 builds the partial
  feature matrix and records the outcome. Preferred fix: compile the kernel
  module whenever *any* of the three native features is enabled, regardless of
  architecture, and `cfg` only the token variants per architecture, so the crate
  always names `fearless_simd` when a feature has pulled it in. A platform with
  no matching token then selects `Legacy` through the ordinary policy rather
  than through a missing module. If that still leaves a configuration with an
  unused dependency, document a narrowly scoped allow with its reason; a global
  silence is not acceptable.
- **Risk: lint friction.** The workspace denies `float_arithmetic`,
  `indexing_slicing`, `unwrap_used`, `expect_used`, `integer_division`, and
  `missing_docs_in_private_items`. Severity: low. Likelihood: high. Mitigation:
  the kernel uses `get`/`chunks_mut` idioms already present in
  `portable_simd.rs:41-52` instead of indexing, and any `#[expect]` carries a
  scoped reason.
- **Risk: MSRV drift in a caret requirement.** `fearless_simd = "1.2"` permits
  any 1.x, and a later 1.x may raise its MSRV. Severity: low. Likelihood: low.
  Mitigation: `--locked` builds, record the resolved version, and re-run the
  1.89 check at adoption.

## Surprises & discoveries

Reconnaissance findings that change what the implementation must do. Each is
recorded with its evidence so that a later reader does not have to rediscover
it.

- Observation: the `padded_point_count()` accessor is only compiled under
  `test`, `kani`, or a *legacy* SIMD feature plus architecture. Evidence:
  `chutoro-providers/dense/src/simd/point_view.rs:123-139`. Impact: a generic
  kernel compiled under a new gate could not call it. EP-M3 must extend that
  `cfg` list, and the plan treats it as an expected file edit rather than a
  surprise mid-milestone.
- Observation: the x86 query kernels use **aligned** loads while the pairwise
  kernels use unaligned loads. Evidence: `_mm512_load_ps`/`_mm256_load_ps` at
  `simd/kernels/x86_simd.rs:139` and `:177`, against `*_loadu_ps` in the
  pairwise macro at `:43-44`. Impact: alignment is a load-bearing precondition
  of the current query kernels, not an optimization detail. The generic kernel
  reads through safe slice operations, which relaxes it; that is a change in
  the *precondition*, not in behaviour, and must be stated in the design update.
- Observation: no query kernel has a scalar remainder today; every one assumes
  the native lane width divides the 16-point padding unit. Evidence:
  `step_by($lanes)` over `padded_count` in `simd/kernels/x86_simd.rs:84` and
  `neon_simd.rs:61`; `out.chunks_mut(16)` in `portable_simd.rs:45`;
  `lane_output_count` only truncates writes (`simd/mod.rs:31`). The Kani
  harness hard-codes lane widths `[4, 8, 16]` (`kani_proofs.rs:129-137`).
  Impact: RFC 0001's "complete chunks and a scalar remainder independent of the
  padding width" is new behaviour, not a restatement. It needs its own
  invariant, test, and proof, and it is the one place the new kernel is
  *stronger* than every existing one.
- Observation: the plan's own first-draft remainder lemma was wrong, and the
  error is a real implementation hazard.
  Evidence: with `n = 17`, `P = 32`, and `L = 16`, the first full chunk covers
  `0..16` and the loop advances `start` to 32, which is **greater than `n`**.
  A remainder loop written `for index in start..n` either panics or, if written
  with unsigned subtraction, wraps. The existing kernels never hit this because
  they iterate `padded_count` and discard writes past `out.len()` via
  `lane_output_count` (`simd/mod.rs:31`, `x86_simd.rs:97`).
  Impact: `L-chunk-partition` now states `start = L * floor(P / L)` and requires
  the remainder to be `min(start, n)..n`. The kernel must guard on
  `start < n` before iterating, and the Kani harness must include a case where
  `start > n`, which the `n = 17`, `L = 16` pair supplies.
- Observation: `Level` does not implement `Simd`, so the kernel cannot be called
  through a `Level` value at all.
  Evidence: compiler diagnostics on 2026-11-24 from a scratch crate that called
  a `<S: Simd>` function with `Level::new()`;
  `error[E0277]: the trait bound fearless_simd::Level: fearless_simd::Simd is
  not satisfied`, listing `Avx2`, `Avx512`, `Sse2`, and `Sse4_2` as
  implementors.
  Impact: `FearlessToken` is structurally necessary, not stylistic, and the
  design must match on the level before it can call the kernel. It also means a
  `Level`-shaped cache would not compile, which the plan's `QueryInvocation`
  already avoids.
- Observation: RFC 0001's claim that the contract "requires zero distances for
  identical zero vectors" is stronger than the code. Evidence:
  `ZeroVectorPolicy::ReturnZero` is a declarative variant;
  `debug_assert_contract` only asserts the variant is still `ReturnZero`
  (`simd/semantics.rs:182-191`), and every zero-row fixture is compared through
  the same `1.0e-5` epsilon. Impact: the plan does not add an exact-zero
  assertion; it preserves the measured contract. REQ-F3 is restated precisely
  below.
- Observation: `chutoro-providers/dense/Cargo.toml` declares no `rust-version`,
  and only `chutoro-core` declares one. Evidence:
  `chutoro-providers/dense/Cargo.toml:1-4`; `chutoro-core/Cargo.toml:5`;
  workspace `Cargo.toml:19`. Impact: Constraint 11 exists because RFC 0001
  requires effective MSRV metadata, and no CI lane builds under 1.89 either
  (see the next finding).
- Observation: there is no MSRV continuous-integration lane, and no
  `make deny`/`cargo-deny` target, despite a dependency being added by this
  work. Evidence: `.github/workflows/` contains no 1.89 job; the Makefile has no
  `deny` target and the repository has no `deny.toml`. Impact: MSRV evidence
  must be produced locally with `cargo +1.89` and recorded in the plan; the
  plan does not invent a CI lane or a deny policy.
- Observation: no benchmark target measures the dense distance kernel in
  isolation, and `DensePointView` is `pub(crate)`, so level 1 of RFC 0001's
  measurement cannot be expressed from `chutoro-benches` today. Evidence:
  `DensePointView` at `simd/point_view.rs:70` re-exported `pub(crate)` at
  `simd/mod.rs:19`; the kernel entry is private at `simd/mod.rs:126`;
  `chutoro-benches` bench targets are `hnsw`, `hnsw_ef_sweep`, `edge_harvest`,
  `mst`, `pipeline`, `extraction`, and `neighbour_scoring` only. The `testing`
  feature exposes Arrow fixtures, not kernel seams (`lib.rs:19-20`). Impact:

- Observation: `docs/chutoro-design.md` still names `simd/kernels.rs` in two

## Decision log

- D1. Decision: the candidate is a single private generic function in a new file
  `chutoro-providers/dense/src/simd/kernels/fearless.rs`, gated on an existing
  SIMD feature plus architecture. Rationale: it sits beside the bodies it would
  replace, keeps `kernels/mod.rs` under the 400-line cap, and adds no public
  surface. The rejected alternative — extending `kernels/mod.rs` — would push
  that file past 400 lines once tests are included. Date/Author: 2026-11-24,
  planning agent.
- D2. Decision: the generic kernel loops chunk-outer and dimension-inner, reads
  each coordinate block through safe slice access, and covers the tail with a
  scalar remainder driven by the block length rather than by the padding unit.
  Rationale: this reproduces the existing lane-per-candidate arithmetic exactly
  (same per-lane operation order, same separate multiply and add), while making
  the kernel correct for any native width rather than only for widths that
  divide 16. The rejected alternative — mirroring `out.chunks_mut(width)` as
  the portable-SIMD body does — reads past the block when the native width
  exceeds the padded length, which a future 32-lane backend would trigger.
  Date/Author: 2026-11-24, planning agent.
- D3. Decision: do not add `fearless_simd_macros` initially; use the manual
  inlining route (`#[inline(always)]` plus `Simd::vectorize`). Rationale: the
  crate already dispatches itself, so the macro's multiversioning duplicates a
  decision the selector owns, and it pulls procedural-macro dependencies into a
  crate that currently has none. The feasibility probe made that cost concrete:
  declaring the macro crate without using it produced
  `cargo::unused_dependencies` for `fearless_simd_macros`, which under
  `-D warnings` is a gate failure. If EP-M2's disassembly inspection shows
  scalar code in the hot loop, the macro is added and the decision is revised
  with that evidence. Date/Author: 2026-11-24, planning agent.
- D4. Decision: obtain the token after the existing selector has chosen a
  backend, never instead of it, and never through `dispatch!`. Rationale: RFC
  0001 and ADR 0007 both require that public feature choices survive.
  `dispatch!` can enable an instruction set that `--no-default-features`
  excluded, so it is forbidden even though it is the library's documented
  convenience path. Date/Author: 2026-11-24, planning agent.
- D5. Decision: the substitution policy is a pure `const fn` over the selected
  backend, a token-availability record, and a compile-time execution-evidence
  set; the runtime step only converts real tokens. Rationale: it makes the
  eligibility rule exhaustively testable and Kani-checkable without modelling
  the library, and it makes the evidence gate auditable in source rather than
  in prose. The rejected alternative — branching directly on `Option<Token>` at
  the call site — is untestable without hardware. Date/Author: 2026-11-24,
  planning agent.
- D6. Decision: only the AVX2 backend is a substitution candidate on this host.
  AVX-512 and NEON compile, are selected by the existing selector, and keep
  their legacy query bodies. Rationale: RFC 0001 T5 requires native execution
  before enabling a replacement, and this host has no AVX-512 and no AArch64
  execution. Date/Author: 2026-11-24, planning agent.
- D7. Decision: level-1 (packed-kernel) measurement uses a
  `#[cfg(feature = "testing")]`, `#[doc(hidden)]` fixture in the dense crate
  that owns a packed view, a query, and an output buffer, and can run a named
  backend and kernel variant. `chutoro-benches` enables the `testing` feature.
  Rationale: RFC 0001 requires an isolated measurement that reuses an
  already-constructed view, and no such seam exists. The `testing` feature is
  already a documented test-support surface, so the addition is consistent with
  its purpose, and `#[doc(hidden)]` keeps it out of the documented API. It is
  still a public item, so Q1 asks for confirmation; if declined, level 1 is
  recorded as unmeasurable and the level-2 gate alone decides. Date/Author:
  2026-11-24, planning agent.
- D8. Decision: the differential suite adds a test-local naive oracle written
  directly from the distance definition, independent of
  `kernels::euclidean_distance_query_points_scalar`. Rationale: the kernel's
  scalar remainder will share the scalar kernel's per-index helper, so an
  oracle that delegates to that kernel would not be independent for the
  remainder path. The existing `DistanceSemantics::oracle_query_points` remains
  for the current backends. Date/Author: 2026-11-24, planning agent.
- D9. Decision: no Verus proof. Bounded model checking plus property tests carry
  the obligations. Rationale: see `Verification plan`,
  `Formal verification decision`. Date/Author: 2026-11-24, planning agent.
- D10. Decision: `insta` snapshots are not used; `rstest-bdd` is not added to
  the dense crate. Rationale: no multivariant output format changes, and adding
  `rstest-bdd` would be an unauthorized dev-dependency in a crate with no
  behavioural suite. The proposed acceptance scenarios are expressed as named
  `rstest` cases instead. Date/Author: 2026-11-24, planning agent.
- D11. Decision: adoption requires at least a 10% net reduction in the complete
  maintained query-kernel surface, counting retained legacy bodies, dispatch,
  query tests, and the query proof harness. Rationale: RFC 0001 requires a
  "useful" net reduction but does not quantify it. Ten percent is small enough
  to be achievable by a genuine consolidation and large enough not to be
  satisfied by deleting a comment. This operationalization needs maintainer
  confirmation at approval. Date/Author: 2026-11-24, planning agent.
- D12. Decision: a null result retains the level-2 benchmark target, the noise
  study, the protocol record, and the documentation update; it removes the
  dependency, the generic kernel, the invocation wiring, the testing seam, the
  level-1 benchmark group, and the kernel proof harness. Rationale: RFC 0001
  forbids leaving an unused backend or trial dependency, but the complete-batch
  benchmark and the noise study are independently useful and fill an identified
  gap. The rejected alternative — reverting everything — would discard the only
  dense distance measurement in the repository. Date/Author: 2026-11-24,

## Context and orientation

### Terms

- **HNSW**: Hierarchical Navigable Small World, the approximate
  nearest-neighbour graph chutoro builds.
- **SoA**: Structure of Arrays. Coordinates are stored one dimension at a time,
  so every point's value for one dimension is contiguous.
- **Kani**: a bounded model checker for Rust. `cargo kani` explores every
  execution within stated unwind and input bounds.
- **Verus**: a deductive verifier for Rust used in this repository for unbounded
  proofs over pure functions.
- **Gate**: a pre-registered measurement whose outcome decides whether work
  continues. A failed gate is a recorded result, not an error.

### Current control flow

The public path is `DataSource::batch_distances` in
`chutoro-core/src/datasource/mod.rs:241-257`, which becomes

## Verification plan

Verification is co-designed with the implementation. The obligations below are
stated before the kernel is designed, so that the design is shaped by what must
be shown rather than the reverse.

### Abstract model

Let the query be `q = (q_0, ..., q_{d-1})` in `f32`, and the candidates
`p_0, ..., p_{n-1}` with `p_i = (p_i[0], ..., p_i[d-1])`. Let

```plaintext
P = n.next_multiple_of(16)                 padding unit, 16
B_k = [p_0[k], ..., p_{P-1}[k]]            coordinate block for dimension k
                                           with p_j[k] = 0 for j >= n
```

`B_k` is exactly `P` elements long and 64-byte aligned. The reference
computation is

```plaintext
S_i = sum over k = 0..d-1, in increasing k order, of (q_k - p_i[k])^2
R_i = let v = sqrt(S_i) in if v is finite then v else NaN
```

where each subtraction, multiplication and addition is one IEEE-754 binary32
operation with round-to-nearest-even, and the accumulation is strictly
left-to-right. The candidate kernel must satisfy: for every `i` in `0..n`,
`out[i]` is exactly `R_i` as computed by the reference, and `out` has no other
written element.

Preconditions: `q.len() == d`; `out.len() == n`; every `B_k` is `P` elements
long; `P` is a multiple of 16; the packed base is 64-byte aligned. Violating a
precondition is a programming error caught by the existing `assert_eq!` at the
safe boundary (`kernels/mod.rs:217-218`), not a recoverable error.

Malformed input (a length mismatch) is rejected before the kernel by the
existing checks, and the caller's buffer is not modified.

### Invariants and lemmas

Invariants:

- `INV-visible-output` — for `i` in `0..n`, `out[i]` is written exactly once
  with `R_i`; no other element of `out` is written. Covers REQ-F1, REQ-F3.
- `INV-padding-inert` — lanes whose index is at least `n` are never written and
  never influence a written value. Covers REQ-T3.
- `INV-full-chunk-in-bounds` — every full-width read covers exactly
  `L = S::f32s::LEN` contiguous elements starting at a multiple of `L`, and
  `start + L <= P`. Covers REQ-T3.
- `INV-partition` — the set of indices handled by full chunks and the set
  handled by the scalar remainder are disjoint, and their union is exactly
  `0..n` whenever every full chunk lies inside `0..n`, which holds because
  `start + L <= P` and `P` may exceed `n`. When `P > n`, a full chunk may
  straddle the logical end; such a chunk's lanes at or above `n` are padding and
  are discarded, so the union is `0..n` for the *bytes written*, not for the
  indices read. This distinction must be stated in the kernel's documentation.
  Covers REQ-T3.
- `INV-dimension-order` — per lane, the operations are, in order for each `k`:
  one subtraction `q_k - p[k]`, one multiplication of the delta by itself, one
  addition into the accumulator; no horizontal reduction inside the loop and no
  reordering across `k`. Covers REQ-F2.
- `INV-no-contraction` — the multiply and the add are not fused. Covers
  REQ-F2.
- `INV-single-finalize` — `finalize_distance` is applied exactly once per
  visible index, after the last dimension. Covers REQ-F3.
- `INV-token-provenance` — every token used to execute code came from
  `Level::new()`/`try_detect()` plus `as_avx2`/`as_avx512`/`as_neon`; no
  `assume_supported`, no `dispatch!`, no synthetic mask. Covers REQ-T2.
- `INV-selector-authority` — the generic kernel runs only when
  `dispatch::euclidean_backend()` already selected that backend and the
  pre-registered evidence set contains it. Covers REQ-F4, REQ-T5.
- `INV-no-allocation` — the kernel performs no heap allocation. Covers REQ-T4.
- `INV-pairwise-unchanged` — `EUCLIDEAN_KERNEL`, `squared_l2_tail`, and the
  pairwise branch of `euclidean_distance_batch_pairs` are byte-identical to the
  base revision. Covers REQ-F5.

Lemmas required to connect the invariants to the required behaviour:

- `L-pad-multiple` — `P = n.next_multiple_of(16)` is a multiple of 16, and
  `n <= P`. Source: `point_view.rs:175-177`, `MAX_SIMD_LANES = 16`.
- `L-block-length` — `coordinate_block(k).len() == P` for every
  `k < d`. Source: `PackedSoaStorage::block` (`point_view.rs:61-65`).
- `L-chunk-partition` — for the loop `start = 0; while start + L <= P`, the
  chunk ranges `[start, start + L)` are pairwise disjoint, and after the loop
  `start = L * floor(P / L)`, that is, the largest multiple of `L` not exceeding
  `P`. Two consequences follow, and the plan needs the second, not the first:
  1. `start >= P - L + 1`, so no further full chunk fits.
  2. The remainder must be `[start, n)`, **clamped to `n`**: `min(start, n)` to
     `n`. Because `P >= n`, `start` can exceed `n` (for example `n = 17`,
     `P = 32`, `L = 16` gives `start = 32`), in which case the remainder is
     empty and no index remains. A kernel that blindly iterates `start..n`
     would underflow or panic; one that iterates `min(start, n)..n` is correct
     for every `L` and every `n <= P`.
- `L-visible-count` — for a chunk at `start`, the number of logical points in it
  is `n.saturating_sub(start).min(L)`, which is `0` when `start >= n`.
- `L-lane-arithmetic` — a lane's vector expression computes the same binary32
  value as the scalar expression for the same index and the same `k` order,
  because both perform the same single-rounding operations in the same order.
- `L-finalize` — applying `finalize_distance` once after the last dimension
  yields `R_i`, matching the scalar kernel's post-loop pass
  (`kernels/mod.rs:253-255`).

### Axioms (trusted, not verified here)

- `AXIOM-ieee-lane` — Fearless SIMD's `Sub`, `Mul`, and `Add` on `f32` lanes are
  each a single IEEE-754 binary32 operation with round-to-nearest-even, applied
  lane-wise, with no reassociation and no reduction. Source: `SimdBase` and
  `SimdFloat` documentation, and the absence of any fast-math mode in Rust.
  Depended on by `L-lane-arithmetic`.
- `AXIOM-no-contraction` — the Rust compiler does not contract a separate
  multiply and add into a fused multiply-add for this code. Source: Rust's
  documented floating-point semantics; contracting requires an explicit
  `mul_add`. Corroborated by disassembly evidence in EP-M2, not proved.
- `AXIOM-token-soundness` — a token obtained from `Level`'s safe conversion
  proves the running CPU supports the matching instruction set, and executing
  code compiled for that token is sound. Source: Fearless SIMD's documented
  capability contract. Not verified here; the plan never fabricates a token.
- `AXIOM-chunks-order` — slice iteration (`chunks_mut`, `iter_mut`, `get`)
  yields elements in increasing index order. Source: the standard library.
- `AXIOM-oracle-order` — `euclidean_distance_query_points_scalar` accumulates in
  increasing dimension order and is unchanged by this work. Source: the file's
  current text, guarded by `INV-pairwise-unchanged`'s companion check that the
  scalar kernel's lines are untouched (Constraint 4).
- `AXIOM-avx2-host` — this development host executes x86-64-v3. Source: measured
  `/proc/cpuinfo` flags (`avx`, `avx2`, `fma`, `bmi1`, `bmi2`, `f16c`, `movbe`,
  `abm`, `cx16`, `popcnt`, `sse4_2`, `xsave`), recorded in
  `Artefacts and notes`. Exercised by every AVX2 test run.

### Methods per obligation

- Obligation `INV-dimension-order`, `L-lane-arithmetic`, `INV-single-finalize`,
  `INV-visible-output` (numerical half). Method: parameterized `rstest` cases
  plus a property test, with two independent references. Rationale: these are
  arithmetic equalities over a finite, well-understood operation set; sampled
  properties over a wide input domain plus exact boundaries give proportionate
  rigour, and a naive reference catches a mistake shared between the kernel and
  the scalar kernel it replaces. Domain: candidate counts
  `0, 1, 2, 3, 4, 7, 8, 9, 15, 16, 17, 31, 32, 33, 64, 128`; dimensions
  `0, 1, 3, 8, 16, 33, 128, 768`; values covering `+0.0`, `-0.0`, duplicates,
  subnormals, `f32::MAX`, `f32::MIN`, `±inf`, quiet NaN, and the signalling NaN
  bit pattern `0x7F80_0001`. Property tests use `proptest` with at least 256
  cases in the pull-request tier. Artefact:
  `chutoro-providers/dense/src/simd/tests/fearless.rs`, new module. Evidence:
  `cargo nextest run -p chutoro-providers-dense -E 'test(simd::tests::fearless)'`.
  A deliberately wrong reference (for example, accumulating with `mul_add`)
  must make the bit-identity case fail. Non-vacuity: every count and dimension
  class has at least one named witness; the padding classes (15, 17, 31, 33)
  actually exercise both a full chunk and a remainder on the AVX2 width; the
  property generator's classifier records how many cases had a non-empty
  remainder, and a run with zero such cases is a failure.
- Obligation `INV-padding-inert`, `INV-full-chunk-in-bounds`, `INV-partition`,
  `L-pad-multiple`, `L-block-length`, `L-chunk-partition`, `L-visible-count`
  (index half). Method: bounded model checking with Kani, plus `rstest`
  boundary cases. Rationale: these are universally quantified statements over
  small integers with a stride; exhaustive exploration within explicit bounds
  is stronger than sampling and is exactly what the repository's existing 2.2.7
  harnesses do. Domain: `n` symbolic in `0..=33`, `d` symbolic in `0..=2`, `L`
  symbolic in `{1, 2, 4, 8, 16, 32}` with `P = n.next_multiple_of(16)`. The
  domain must contain an `n` where `start > n` at `L = 16` (`n = 17` gives
  `start = 32`) and an `n` where the remainder is non-empty (`n = 17` at
  `L = 8` leaves one index), so both the clamp and the non-empty remainder
  branches are reachable.
  Artefact: a new harness `verify_dense_simd_fearless_partition` in
  `chutoro-providers/dense/src/simd/kani_proofs.rs`, registered in `make kani`
  if it completes within the verification-cost tolerance. Evidence:
  `make kani`; the harness must fail when the loop bound is mutated from `L` to
  `L - 1`. Non-vacuity: the bound set includes `L` values that divide 16, one
  that does not (32 when `n mod 32 != 0`), and one larger than `P` for small
  `n`, so each remainder branch is reachable; the harness records a failure if
  no `L` and `n` combination produces a non-empty remainder.
- Obligation `INV-token-provenance`, `INV-selector-authority`.
  Method: exhaustive enumeration of the pure policy function, plus a named
  integration test on the real host. Rationale: the policy is a total function
  of three small finite domains, so enumeration is complete; the real-host test
  confirms the token actually obtained matches the recorded expectation.
  Domain: 5 backends × 8 token-availability combinations × 8 evidence-set
  combinations. Artefact: `simd/tests/fearless.rs` policy cases;
  `simd/tests/support_masks.rs` extended with a real-token assertion. Evidence:
  a mutation that enables a backend absent from the evidence set must fail a
  named case. Non-vacuity: the domain includes the `Avx2`-selected-but-no-token
  case, which must return `Legacy(Avx2)`, and the
  `Avx512`-selected-but-not-in-evidence case, which must return
  `Legacy(Avx512)`.
- Obligation `INV-no-contraction`, `REQ-F2` bit identity.
  Method: disassembly inspection plus a bit-identity test against the legacy
  same-backend kernel. Rationale: the property is about generated code, so it
  needs code evidence; the test supplies the numerical guard. Domain: AVX2 only
  on this host, every dimension and count class above. Artefact: an
  `objdump -d` transcript in `Artefacts and notes` showing
  `vsubps`/`vmulps`/`vaddps` and no `vfmadd*` in the kernel body; the
  bit-identity test lives in `simd/tests/fearless.rs`. Evidence:
  `objdump -d --no-show-raw-insn target/release/deps/<bench or test binary>`
  filtered to the kernel symbol; and
  `cargo nextest run -p chutoro-providers-dense -E 'test(legacy_bit_identity)'`.
  Non-vacuity: the test compares against the *legacy* body, not against the
  scalar oracle, so it would catch a change that the >1e-5 tolerance hides; the
  disassembly is quoted, not summarized.
- Obligation `INV-no-allocation`.
  Method: a mechanical statement audit of the kernel module, plus a structural
  argument from its call graph. Rationale: a counting `#[global_allocator]`
  would be a process-global testing override in the dense crate's own test
  binary, which REQ-T4 forbids and which would perturb every other test in that
  binary. The kernel's whole call set is
  `S::f32s::{splat, from_slice, store_slice}`, slice `get`/`get_mut`/`iter`/
  `iter_mut`/`chunks`/`skip`/`take`/`zip`, integer arithmetic, and the scalar
  per-index helper; none of those allocate, so a review that pins the call set
  is decisive without an allocator hook. Domain: every statement in
  `simd/kernels/fearless.rs` and the scalar per-index helper. Artefact: a
  recorded
  `grep -nE 'Vec|Box|String|format!|to_vec|collect|vec!|with_capacity|reserve'`
  over the two files returning no match, plus the `Artefacts and notes`
  transcript. Evidence: the grep is empty; and a deliberately added
  `let _ = Vec::<f32>::new();` makes it non-empty, which is the negative
  control, then is reverted. Non-vacuity: the same grep over `simd/mod.rs`
  returns matches, proving the pattern set detects allocation where allocation
  exists.
- Obligation `INV-pairwise-unchanged`.
  Method: pre/post line-level comparison of the pairwise paths. Rationale: it
  is a no-change claim, so the cheapest decisive evidence is that the relevant
  lines are untouched. Artefact: `git diff` scoped to `EUCLIDEAN_KERNEL`,
  `squared_l2_tail`, the pairwise macro invocation, and
  `collect_euclidean_distance_batch`, recorded in `Artefacts and notes`.
  Evidence: an empty diff for those ranges plus a green
  `cargo nextest run -p chutoro-providers-dense -E 'test(pairwise)'`.
  Non-vacuity: the pairwise parity suite runs and reports a non-zero case count.
- Obligation `REQ-F1` output atomicity and ordering.
  Method: the existing named tests, unmodified. Rationale: the behaviour is
  already specified and pinned; re-deriving it would add no assurance. Artefact:
  `simd/tests/mod.rs:200`, `:220`, `:248`, `:316`. Evidence: they pass in
  every milestone. Non-vacuity: `batch_pairs_leave_output_unmodified_on_error`
  uses a sentinel buffer, so a silent partial write fails it.

### Formal verification decision

No Verus proof is planned. The obligations that matter here are (a) bounded
index arithmetic over small integers with a stride, and (b) an equality between
a vector expression and a scalar expression under IEEE-754. Obligation (a) is
exactly the shape bounded model checking handles better than a deductive proof:
Kani explores every admissible `n`, `d`, and `L` within stated bounds, and the
existing 2.2.7 harnesses establish that this is tractable in this crate.
Obligation (b) cannot be established by a Rust-level proof at all, because it
depends on `AXIOM-ieee-lane` and `AXIOM-no-contraction`, which describe the
library and the code generator rather than chutoro's own logic; a Verus proof
would either assume them or restate them. The repository's Verus proofs
(`verus/edge_harvest_proofs.rs`, `verus/session_core_distance.rs`) cover
contractual business logic over unbounded inputs, which this change does not
introduce: the distance contract is unchanged and the scalar oracle is
untouched. The dispatch policy is a total function over finite domains, where
exhaustive enumeration is strictly stronger than a proof. Recorded as D9.

Residual gap: Kani does not model Fearless SIMD's vectors, and no harness
claims to. The harnesses prove chutoro's own index arithmetic and policy only.

### Suggested BDD features

The dense crate has no `rstest-bdd` runner, and adding one would be an
unauthorized dev-dependency, so no feature file is added (D10). The observable
acceptance behaviour is expressed as named `rstest` cases instead. The proposed
wording, for the design update and for reviewers, is:

```gherkin
Feature: Dense query-to-points distance is unchanged by the kernel substitution
  Scenario: A shared-query batch returns the same distances
    Given a dense matrix whose rows 1 to 33 are candidates for row 0
    When the provider scores row 0 against those candidates
    Then each returned distance matches the scalar reference within 1.0e-5
    And the result count equals the candidate count

  Scenario: A non-finite candidate is reported as NaN
    Given a query containing positive infinity
    When the provider scores it against a finite candidate
    Then the returned distance is NaN

  Scenario: Padding never becomes a result
    Given 17 candidates, so the packed block holds 32 lanes
    When the provider scores them
    Then exactly 17 distances are written
    And the caller's buffer has no nineteenth element written
```

Mapping: the first scenario is
`simd::tests::fearless::naive_oracle_parity_over_counts_and_dimensions`; the
second is `simd::tests::fearless::non_finite_canonicalization`; the third is
`simd::tests::fearless::padding_is_never_visible` plus the Kani harness. The
`DistanceSemantics` contract object (`simd/semantics.rs:59-64`) remains the
single place the tolerance and non-finite policy are defined.

## Performance experiment and preregistration

This section is committed before any candidate code and before any candidate
timing. It is the pre-registration RFC 0001 requires. Changing it after a
measurement requires a dated `Revision note` entry and a `Decision log` entry
naming the reason.

### Inputs and matrix

| Level          | What is timed                                                                                                                  | Candidate counts                                  | Dimensions                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- | ------------------------- |
| Packed kernel  | The kernel only, over a pre-built packed view and a preallocated output                                                        | 0, 1, 2, 4, 8, 16, 32, 64, 128                    | 0, 1, 8, 16, 32, 128, 768 |
| Complete batch | `DenseMatrixProvider::batch_distances`, including shared-query detection, validation, packing, allocation, and result transfer | 0, 1, 2, 4, 8, 16, 24, 32, 48, 64, 128, 256, 1024 | 0, 1, 8, 16, 32, 128, 768 |

*Table 4: Pre-registered measurement matrix. Counts 24, 48, 256, and 1024 come
from the existing `neighbour_scoring` plan
(`chutoro-benches/src/neighbour_scoring/benchmark_plan.rs:4-9`) and represent
real HNSW buckets, so a level-2 conclusion reflects a workload callers actually
run.*

Controls that must not drift: candidate counts 0 and 1 and every dimension 0

`simd/mod.rs:148-154`), so they are scope-drift controls and are gated only at

### Instrument and protocol

- Instrument: Criterion 0.5.1 through a new `dense_distance` target in
  `chutoro-benches`, `harness = false`, registered in
  `chutoro-benches/Cargo.toml`.
- Corroboration: `hyperfine` 1.20.0 through a new
  `scripts/bench-dense-distance.sh`, modelled on
  `scripts/bench-neighbour-scoring.sh:22-55`: build with
  `cargo bench -p chutoro-benches --bench dense_distance --no-run --message-format=json`,
  extract the executable with `jq`, then run it with
  `--bench --profile-time 2`. Treat `hyperfine` as corroboration; Criterion and
  cycle counts remain the primary signal, per
  `docs/developers-guide.md:2934-2935`.
- Pairing: baseline and candidate binaries are built from two worktrees at the
  same commit graph and run **interleaved** in one `hyperfine` invocation, so
  drift in machine state affects both. Use a positional Criterion filter, not
  `--exact`: this repository intercepts the literal `--exact` flag to mean a
  bounded probe (`is_exact_benchmark_probe_args`,
  `chutoro-benches/src/criterion_support.rs:60-69`), and several targets switch
  to reduced sizes or no-op registration when they see it. An `--exact` run
  would therefore measure the probe path rather than the workload.

  ```sh
  taskset -c 4-7 hyperfine --warmup 3 --runs 20 \
    --export-json /tmp/hyperfine-dense-distance.json \
    "$BASELINE --bench --profile-time 2 'dense_distance/batch/dim_128_candidates_32'" \
    "$CANDIDATE --bench --profile-time 2 'dense_distance/batch/dim_128_candidates_32'"
  ```

  `--profile-time` is the argument the existing helper script uses
  (`scripts/bench-neighbour-scoring.sh:50-55`): it runs each case for a fixed
  wall-clock period and suppresses Criterion's own statistics, which is what
  makes the process a stable `hyperfine` subject.
- Criterion: save a baseline on the base revision and compare on the candidate,
  both under `taskset -c 4-7`:

  ```sh
  cargo bench -p chutoro-benches --bench dense_distance -- --save-baseline run-1
  cargo bench -p chutoro-benches --bench dense_distance -- --baseline run-1
  ```

  Never compare against a stored baseline from another day.
- Fixed inputs: `BENCH_SEED = 0` plus explicit per-case value generation, so
  both binaries measure the same data.
- Release builds, warmed caches, one thread (the kernel is single-threaded;
  `RAYON_NUM_THREADS` is pinned anyway so a future parallel caller cannot
  confound the comparison).
- Separate initialization from steady state: construction of the packed view and
  the output buffer happens outside the timed closure at level 1.
- Record with every result: host model, `rustc --version`, resolved
  `fearless_simd` version, enabled Cargo features, the selected backend, and
  the measured token availability.

### Noise establishment

Before any candidate timing, run five unchanged-versus-unchanged Criterion
comparisons at the decision sizes on the base revision. The instrument passes
at a given cell only if the 95% confidence interval half-width of the relative
change is at most 1.0%, **or** at most `max(1.0%, 2.0 ns / measured time)`,
whichever is larger.

The second term exists because Criterion cannot resolve a sub-10 ns cell to 1%:
its own timer resolution and per-iteration overhead dominate, and demanding 1%
there would manufacture an inconclusive verdict for reasons unrelated to the
kernel. The escape clause is bounded: it never relaxes a cell whose measured
time exceeds 200 ns, because at that point 2 ns is under 1% anyway. Every cell
that uses the clause is marked as such in the evidence table, with its measured
time and half-width.

Sizing: gate all four dimension classes (32, 128, 768) at the decision counts,
plus the dimension 8 class as a diagnostic. Cells whose measured time is under
2 ns are reported as unmeasurable rather than gated; that is a recorded limit
of the instrument, not a pass.

If a cell fails after one tightening pass (higher sample size, longer
measurement time, pinned cores), the experiment is inconclusive at that cell
and is recorded with the observed half-width rather than being accepted as
equivalent.

### Decision tolerances

The upper bound of the 95% confidence interval of the relative change,
candidate against baseline, must be within the following limits.

| Size class                              | Level            | Limit                |
| --------------------------------------- | ---------------- | -------------------- |
| Candidates 0, 1; dimension 0 (controls) | batch and packed | no gate; report only |
| Candidates 8                            | batch            | +5.0%                |
| Candidates 16, 24, 32, 48               | batch            | +3.0%                |
| Candidates 64, 128, 256, 1024           | batch            | +2.0%                |
| Candidates 2, 4                         | batch and packed | no gate; report only |
| Candidates 16, 32, 64, 128              | packed           | +3.0%                |

*Table 5: Pre-registered regression limits. The limits are one-sided: any
improvement is acceptable, and no speed-up is required.*

Why two classes are reported but not gated. Candidates 0 and 1 and dimension 0
never enter the packed kernel at all: `should_pack_query_points_for_backend`
requires `dimension > 0 && candidate_count > 1`
(`chutoro-providers/dense/src/simd/mod.rs:148-154`). Gating them would fail the
plan for a change the kernel cannot cause, so they are scope-drift *controls*:
a measurable change there means something outside the kernel moved, and that is
reported and investigated rather than scored. Candidates 2 and 4 are ungated
because one native vector covers them at every width in the matrix, so the cell
measures dispatch and call overhead rather than arithmetic; it is still
reported, because a dispatch regression would show there first.

Rules:

1. Adoption requires every gated cell to be within its limit, for every
   dimension in the matrix, on the same host in the same session.
2. A packed-kernel regression must be reported even when the complete-batch
   number hides it.
3. No pipeline benefit may be claimed from any of these measurements, and no
   end-to-end speed-up is required for adoption.
4. An interval that straddles a limit, or whose half-width exceeds the noise
   rule in `Noise establishment`, is inconclusive rather than a pass.

## Maintenance accounting

RFC 0001 requirement T1 makes the maintenance reduction the deciding gate, so
its arithmetic is pre-registered here.

Counted surface, all in `chutoro-providers/dense/src/simd/` unless stated:

1. every packed query-to-points arithmetic body, including retained legacy
   bodies and the scalar oracle;
2. the query-to-points dispatch: the invocation type, the policy function, the
   cached static, and the match that invokes a kernel;
3. every test whose subject is the packed query kernel, including the new
   differential suite;
4. the packed-query Kani harness, including the new partition harness;
5. the new dependency's manifest lines and the new benchmark support seam.

Method: count non-blank, non-comment lines in the named items at the base
revision and at the candidate, using the same
`git show <rev>:<path> | <command>` invocation for both so the numbers are
comparable. Record both columns and the difference in
`Outcomes & retrospective`.

Adoption rule (D11): the complete patch must show at least a **10% net
reduction** in that counted surface. Deleting a body while adding an equivalent
body elsewhere does not count. Retaining every legacy body while adding a
generic body will, on this analysis, fail the rule, and that is a recorded null
result rather than a defect in the work.

**Partial-feature coverage hazard.** Attaching `dep:fearless_simd` to all three

dependency is then unused-but-linked for that target, which is harmless for
correctness and required for the kernel to exist when the token is available,
but it does mean the level-1 benchmark must report which backend actually ran
rather than which feature was enabled. EP-M3's feature-matrix table records both.

**Architecture coverage.** On a target that is neither x86 nor ARM (for example
`wasm32`), all three features may be enabled while no kernel is compiled. The
`fearless_simd` gate must therefore include `any(target_arch = "x86",
target_arch = "x86_64", target_arch = "arm", target_arch = "aarch64")`, so the
dependency stays declared but unused there. `cargo check --all-features` on such

/// Euclidean distances from one query row to every packed candidate point.
///
/// One lane holds one candidate's running sum of squared differences, so the
/// dimension loop is inside the candidate-chunk loop. Each full chunk covers
/// exactly `S::f32s::LEN` candidates, and the candidates past the last full
/// chunk are finished by the scalar remainder.
fn euclidean_distance_query_points_fearless<S: Simd>(
    simd: S,
    query: &[f32],
    points: &DensePointView<'_>,
    out: &mut [f32],

Required items at the end of `EP-M3`, in
`chutoro-providers/dense/src/simd/kernels/mod.rs`:

```rust
/// Which native backends this CPU's safe tokens prove available.
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
struct TokenAvailability {
    avx2: bool,
    avx512: bool,
    neon: bool,
}

/// Which backends have recorded native execution evidence.
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
struct EvidenceSet {
    avx2: bool,
    avx512: bool,
    neon: bool,
}

/// The implementation a query-to-points call will use, and for which backend.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum QueryKernelChoice {
    Fearless(EuclideanBackend),
    Legacy(EuclideanBackend),
}

/// Pure policy: the selected backend decides; the token and the evidence
/// decide whether the generic kernel is allowed to answer.
const fn choose_query_kernel(
    backend: EuclideanBackend,
    tokens: TokenAvailability,
    evidence: EvidenceSet,
) -> QueryKernelChoice;

/// A safely obtained capability token, one variant per compiled native feature.
enum FearlessToken {
    Avx2(fearless_simd::Avx2),
    Avx512(fearless_simd::Avx512),
    Neon(fearless_simd::Neon),
}

/// What the cached query path will do for the rest of the process.
enum QueryInvocation {
    Fearless(FearlessToken),
    Legacy(EuclideanQueryPointsKernel),
}

static EUCLIDEAN_QUERY_POINTS_INVOCATION: OnceLock<QueryInvocation>;
```

Reuse policy: the generic kernel is owned by the dense provider, is private, is
called only from `kernels::euclidean_distance_query_points`, and must not be
exported, duplicated in `chutoro-core`, or reused through `DensePointView`.
`chutoro-core` must not gain a dependency on the dense provider. This follows
ADR 0007's ownership boundary and must be recorded in the developers' guide as
part of EP-M5.

## Open questions for the maintainer

These need answers before or during approval because they change what the plan
does. The plan's default is stated for each.

- **Q1. The level-1 measurement seam.** RFC 0001 requires an isolated
  packed-kernel benchmark, but `DensePointView` is `pub(crate)` and the kernel
  entry is private, so `chutoro-benches` cannot reach them. D7 proposes a
  `#[cfg(feature = "testing")]`, `#[doc(hidden)]` fixture in the dense crate.
  That is a new public item, behind a non-default test-support feature, and the
  RFC forbids a new public abstraction. Default if declined: level 1 is
  recorded as unmeasurable and only the complete-batch gate decides.
- **Q2. Execution hosts.** RFC 0001 T5 requires native execution before a
  backend is substituted, and this host has neither AVX-512 nor AArch64.
  Default: AVX2-only substitution, with AVX-512 and NEON reported as compiled,
  selected, and not executed. If an Ice Lake-class and an AArch64 host can be
  provided, the plan gains two more substitution candidates and the maintenance
  gate becomes reachable.
- **Q3. Retaining the AVX2 legacy body.** RFC 0001 requires a missing token to
  fall back to the legacy body the selector chose, so the AVX2 body stays and
  the maintenance gate probably fails. Would the maintainer accept amending
  that rule to allow falling back to the *scalar* oracle when the v3 token is
  absent? Default: no — the RFC rule stands and a null result is recorded.
- **Q4. The 10% maintenance rule (D11).** Is 10% the intended reading of "a
  useful net reduction", or should the threshold be different? Default: 10%.
